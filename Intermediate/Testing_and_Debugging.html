Testing and Debugging

Why Test?

Python is a dynamic language: there is no compiler that checks your types, and many mistakes (a misspelled attribute, a wrong argument, a None where a list was expected) only show up when the faulty line actually runs. That flexibility is great while writing code, but it means the only way to be confident that a program works is to run it and check the results. A test is simply code that does this for you, automatically and repeatably.

Tests give you several concrete benefits:
  • They catch bugs early, while the code is fresh in your mind and the fix is cheap.
  • They make change safe. When you refactor or add a feature, re-running the tests tells you within seconds whether you broke something that used to work (a regression).
  • They document behavior. A test named test_empty_cart_total_is_zero explains exactly what the code is supposed to do, and unlike a comment it can never silently become outdated.
  • They improve design. Code that is hard to test (functions that do five things, hidden global state) is usually hard to understand too. Writing tests nudges you toward small, focused functions.
Debugging is the other half of the story: when a test fails (or a user reports a problem), you need tools to find out why. This chapter covers both: first how to write tests with assert, unittest and pytest, then how to investigate problems with print(), repr(), logging and the interactive debugger pdb.
Kinds of tests
Kind What it checks Example
Unit test One small piece (a function or a class) in isolation slugify("Hello World") == "hello-world"
Integration test Several pieces working together Saving an order really writes a row to the database
End-to-end test The whole program as a user sees it Running the command-line tool and checking its output
This page focuses on unit tests, which are fast, precise and the foundation of everything else.

Using assert

The simplest test tool is built into the language: the assert statement. It evaluates an expression and does nothing if the result is truthy. If the result is falsy it raises an AssertionError, optionally with a message you supply after a comma: 
assert condition, "optional message shown when condition is false"
Here we check a small average() function with a few known inputs and outputs: 
def average(numbers):
    return sum(numbers) / len(numbers)

assert average([1, 2, 3]) == 2
assert average([10]) == 10
assert average([1, 2]) == 1.5, "average of 1 and 2 should be 1.5"
print("All checks passed!")  # All checks passed!
Now imagine someone "optimizes" the function and accidentally uses floor division //. The assertion fails and the program stops with a traceback pointing straight at the broken check. Including the actual value in the message makes the failure much easier to understand: 
def average(numbers):
    return sum(numbers) // len(numbers)   # bug: floor division

assert average([1, 2]) == 1.5, f"expected 1.5, got {average([1, 2])}"

Traceback (most recent call last):
  File "assert_fail.py", line 4, in <module>
    assert average([1, 2]) == 1.5, f"expected 1.5, got {average([1, 2])}"
AssertionError: expected 1.5, got 1

Comparing floats

Floating-point numbers are stored in binary and cannot represent most decimal fractions exactly, so an exact == comparison can fail even when the math is "right". Compare floats with a tolerance instead, using math.isclose() (or the equivalents in unittest and pytest shown later): 
import math
print(0.1 + 0.2 == 0.3)               # False
print(0.1 + 0.2)                      # 0.30000000000000004
print(math.isclose(0.1 + 0.2, 0.3))   # True

Limits of assert

Plain assert statements are great for quick checks, but as a testing strategy they fall short: the first failure stops the whole script, so you never learn whether the other checks would have passed; there is no report of how many checks ran; and there is no way to run only some of them. Test frameworks such as unittest and pytest solve exactly these problems.
Never put parentheses around the condition and the message together: assert (x == 10, "x should be 10") asserts a non-empty tuple, which is always truthy, so the assertion can never fail. Python 3.12 prints SyntaxWarning: assertion is always true, perhaps remove parentheses? to warn you.
Assertions are removed entirely when Python runs with the -O (optimize) flag. Use assert for tests and for internal "this can never happen" sanity checks, but never to validate user input or enforce security rules; raise a proper exception such as ValueError for that.

Testing a Function with unittest

The unittest module ships with Python, so it is always available. Its model is simple:
  1. Create a class that inherits from unittest.TestCase.
  2. Add methods whose names start with test. Each one is an independent test.
  3. Inside each method, check results with the self.assert...() methods.
Unlike a bare assert, a failing check only fails that test; the runner carries on with the rest and gives you a summary at the end. Let's test a small module, text_utils.py: 
# text_utils.py
def slugify(title):
    """Turn 'Hello World!' into 'hello-world'."""
    if not isinstance(title, str):
        raise TypeError("title must be a string")
    words = "".join(ch if ch.isalnum() else " " for ch in title).split()
    return "-".join(word.lower() for word in words)


def word_count(text):
    """Return a dict mapping each word to how many times it appears."""
    counts = {}
    for word in text.lower().split():
        counts[word] = counts.get(word, 0) + 1
    return counts
The tests live in a separate file whose name starts with test_. Notice how each test checks one behavior and has a descriptive name, and how the edge cases (an empty string, a wrong type) get their own tests: 
# test_text_utils.py
import unittest

from text_utils import slugify, word_count


class TestSlugify(unittest.TestCase):

    def test_simple_title(self):
        self.assertEqual(slugify("Hello World"), "hello-world")

    def test_punctuation_is_removed(self):
        self.assertEqual(slugify("Python: Tips & Tricks!"), "python-tips-tricks")

    def test_result_is_lowercase(self):
        result = slugify("LOUD TITLE")
        self.assertTrue(result.islower())

    def test_empty_string(self):
        self.assertEqual(slugify(""), "")

    def test_non_string_raises_type_error(self):
        with self.assertRaises(TypeError):
            slugify(42)


class TestWordCount(unittest.TestCase):

    def test_counts_repeated_words(self):
        counts = word_count("the cat and the hat")
        self.assertEqual(counts["the"], 2)
        self.assertIn("hat", counts)
        self.assertNotIn("dog", counts)

    def test_is_case_insensitive(self):
        self.assertEqual(word_count("Go go GO"), {"go": 3})


if __name__ == "__main__":
    unittest.main()

Compare the two failure messages: assertEqual tells you what was different, while assertTrue can only say "False is not true". That is why you should always use the most specific assert method available.

The most useful assert methods
Method Checks that
assertEqual(a, b) / assertNotEqual(a, b) a == b / a != b
assertTrue(x) / assertFalse(x) bool(x) is True / False
assertIs(a, b) / assertIsNone(x) a is b / x is None
assertIn(a, b) / assertNotIn(a, b) a in b / a not in b
assertIsInstance(obj, cls) isinstance(obj, cls)
assertAlmostEqual(a, b) round(a - b, 7) == 0 (safe for floats)
assertRaises(Error) the code inside the with block raises Error
Test names should describe behavior, not implementation: test_empty_string or test_non_string_raises_type_error tell you what broke the moment they fail; test_1 tells you nothing.
A method that does not start with test (for example check_title) is silently ignored by the runner. If your test count looks too low, check the method names.

Testing a Class

Testing a class usually means creating an object, putting it into some state, calling a method and checking the result. When several tests need the same starting object, repeating that set-up code in every method is tedious and error-prone. unittest solves this with two special methods:
  • setUp() runs before each test method. Store whatever the tests need on self.
  • tearDown() runs after each test method, even when the test failed, so it is the place to release resources (close files, delete temporary data).
Because setUp() runs again for every test, each test receives a brand-new object. One test can never be affected by changes another test made, which keeps tests independent and lets them run in any order. Here is a class to test: 
# cart.py
class ShoppingCart:
    def __init__(self):
        self.items = {}          # name -> (price, quantity)

    def add_item(self, name, price, quantity=1):
        if price < 0:
            raise ValueError("price cannot be negative")
        old_price, old_qty = self.items.get(name, (price, 0))
        self.items[name] = (price, old_qty + quantity)

    def remove_item(self, name):
        if name not in self.items:
            raise KeyError(f"{name!r} is not in the cart")
        del self.items[name]

    def total(self):
        return sum(price * qty for price, qty in self.items.values())

# test_cart.py
import unittest

from cart import ShoppingCart


class TestShoppingCart(unittest.TestCase):

    def setUp(self):
        # Runs before EVERY test method: each test gets a brand-new cart.
        self.cart = ShoppingCart()
        self.cart.add_item("apple", 0.5, quantity=4)
        self.cart.add_item("bread", 2.25)

    def test_total(self):
        self.assertEqual(self.cart.total(), 4.25)

    def test_adding_same_item_increases_quantity(self):
        self.cart.add_item("apple", 0.5, quantity=2)
        self.assertEqual(self.cart.items["apple"], (0.5, 6))

    def test_remove_item(self):
        self.cart.remove_item("bread")
        self.assertNotIn("bread", self.cart.items)
        self.assertEqual(self.cart.total(), 2.0)

    def test_remove_missing_item_raises(self):
        with self.assertRaises(KeyError):
            self.cart.remove_item("milk")

    def test_negative_price_is_rejected(self):
        with self.assertRaises(ValueError) as context:
            self.cart.add_item("mystery", -1)
        self.assertIn("negative", str(context.exception))

    def tearDown(self):
        # Runs after EVERY test, even if the test failed.
        self.cart = None


if __name__ == "__main__":
    unittest.main()

A few things worth noticing:
  • test_remove_item deletes the bread, yet test_total still sees it, because each test got its own cart from setUp().
  • Using assertRaises as a context manager with as context gives you the exception object, so you can also check its message.
  • Tests run in alphabetical order of their method names, not the order you wrote them. Never write a test that relies on another test having run first.
Test the public behavior of a class (what its methods return and which exceptions they raise) rather than every internal detail. Tests that poke at private implementation details break whenever you refactor, even if the class still works correctly.

Organizing Tests and Test Discovery

Once a project has more than a couple of modules, keep the tests in their own tests folder, with one test file per module being tested. A common layout looks like this: 
shop_project/
    shop/
        __init__.py
        cart.py
        text_utils.py
    tests/
        __init__.py
        test_cart.py
        test_text_utils.py
Inside the test files, import the code through its package name, for example from shop.cart import ShoppingCart.

When you run python -m unittest with no arguments, it performs test discovery: starting from the current folder, it searches for files that match the pattern test*.py, imports them, and collects every TestCase class inside. You can also be more specific: 
> python -m unittest                         # discover and run everything
> python -m unittest -v                      # same, listing every test
> python -m unittest discover -s tests -t . -p "test_*.py"   # explicit start dir and pattern
> python -m unittest tests.test_cart                      # one module
> python -m unittest tests.test_cart.TestShoppingCart     # one class
> python -m unittest tests.test_cart.TestShoppingCart.test_total   # one test
> python -m unittest -k remove               # only tests whose name contains "remove"
> python -m unittest -f                      # stop at the first failure
Run these commands from the project root (shop_project), so that both the shop and tests packages can be imported.
Discovery only descends into folders that are importable packages. If tests/ has no __init__.py file, python -m unittest run from the project root quietly reports Ran 0 tests ... NO TESTS RAN. Add an empty tests/__init__.py to fix it.
Never name your own file after a module you import. A file called unittest.py, random.py or test.py in your project shadows the standard library module and produces very confusing import errors.
Make running the tests a habit: run the whole suite before every commit. A test suite is only useful if it is fast enough that you actually run it, so keep unit tests free of slow work such as real network calls.

Introduction to pytest

pytest is a third-party test framework and the most popular choice in the Python world. It is not part of the standard library, so install it first: 
> python -m pip install pytest
Its big idea is that a test is just a function whose name starts with test_, and checks are written with the ordinary assert statement. No class, no self, no special assert methods to memorize. Here are the text_utils tests rewritten for pytest: 
# test_text_utils.py
import pytest

from text_utils import slugify, word_count


def test_simple_title():
    assert slugify("Hello World") == "hello-world"


def test_punctuation_is_removed():
    assert slugify("Python: Tips & Tricks!") == "python-tips-tricks"


def test_non_string_raises_type_error():
    with pytest.raises(TypeError, match="must be a string"):
        slugify(42)


def test_word_count():
    counts = word_count("the cat and the hat")
    assert counts["the"] == 2
    assert "dog" not in counts


def test_float_total():
    assert 0.1 + 0.2 == pytest.approx(0.3)
pytest.raises works like assertRaises, and its match argument also checks the error message (it is a regular expression). pytest.approx compares floats with a sensible tolerance. Run the tests with the pytest command (or python -m pytest); -v lists each test:

Debugging with print() and repr()

When a test fails and the reason is not obvious, the quickest first step is often to print the values involved. There is one trap, though: print() shows the human-friendly form of a value (its str()), which hides exactly the details that cause many bugs. The string "5" and the integer 5 print identically, and trailing spaces or tab characters are invisible.

The built-in repr() returns the developer-friendly form instead, which for built-in types usually looks like the Python code you would write to create the value. Strings appear with quotes, and special characters are shown as escape sequences: 
user_input = "5"
stored_value = 5
print(user_input, stored_value)              # 5 5   (they look identical!)
print(repr(user_input), repr(stored_value))  # '5' 5
print(user_input == stored_value)            # False

name = "Alice "
print("Name:", name, "|")                    # Name: Alice  |
print("Name:", repr(name))                   # Name: 'Alice '

line = "first\tsecond\n"
print(repr(line))                            # 'first\tsecond\n'
f-strings offer two handy shortcuts. {value!r} inserts repr(value), and the "self-documenting" form {expression=} prints the expression's text, an equals sign, and the repr of its value, so you never have to type the variable name twice: 
total = 42
items = ["a", "b"]
print(f"{total=}, {items=}")     # total=42, items=['a', 'b']
print(f"{name=}")                # name='Alice '
print(f"{len(items) * 2 = }")    # len(items) * 2 = 4
print(f"Got {user_input!r}")     # Got '5'
For your own classes, define __repr__ so that debugging output is informative instead of the default <__main__.Point object at 0x...>: 
class Point:
    def __init__(self, x, y):
        self.x = x
        self.y = y

    def __repr__(self):
        return f"Point({self.x!r}, {self.y!r})"


p = Point(3, "4")
print(p)            # Point(3, '4')   (the quotes reveal that y is a string!)
print([p, p])       # [Point(3, '4'), Point(3, '4')]
Containers such as lists and dicts always use repr() for their elements, which is why print(["5"]) shows ['5'] with quotes.
Debug print() calls are easy to forget and end up in finished programs. Remove them once the bug is fixed, or, for diagnostics you want to keep, switch to the logging module described next.

Using the logging Module instead of print

print() is fine for a five-minute investigation, but in a real program you want diagnostic messages that you can turn on and off without editing the code, that carry a timestamp and a severity, and that can go to a file instead of cluttering the console. The standard logging module provides all of that.

Every message has a level. You choose a threshold, and messages below it are simply ignored:
Level Use it for
DEBUG Detailed information useful only while diagnosing a problem
INFO Confirmation that things are working as expected
WARNING Something unexpected happened, but the program continues (the default threshold)
ERROR A problem prevented some operation from completing
CRITICAL A serious error; the program may not be able to continue 
import logging

logging.basicConfig(
    level=logging.DEBUG,
    format="%(asctime)s %(levelname)-8s %(name)s: %(message)s",
    datefmt="%H:%M:%S",
)
logger = logging.getLogger("orders")


def apply_discount(price, percent):
    logger.debug("apply_discount(price=%r, percent=%r)", price, percent)
    if not 0 <= percent <= 100:
        logger.error("Invalid discount %s%%; returning original price", percent)
        return price
    new_price = round(price * (1 - percent / 100), 2)
    logger.info("Discounted %.2f to %.2f", price, new_price)
    return new_price


apply_discount(80, 25)
apply_discount(80, 150)

21:29:13 DEBUG    orders: apply_discount(price=80, percent=25)
21:29:13 INFO     orders: Discounted 80.00 to 60.00
21:29:13 DEBUG    orders: apply_discount(price=80, percent=150)
21:29:13 ERROR    orders: Invalid discount 150%; returning original price
Once the bug is fixed you do not delete anything: change level=logging.DEBUG to level=logging.WARNING and only the important messages remain. Add filename="app.log" to basicConfig() and the messages go to a file instead of the screen. 
import logging

logging.basicConfig(level=logging.WARNING)
logger = logging.getLogger(__name__)

logger.debug("Hidden: below WARNING")
logger.info("Hidden: below WARNING")
logger.warning("Disk space is low")      # WARNING:__main__:Disk space is low
logger.error("Could not save file")      # ERROR:__main__:Could not save file

Good habits

  • In each module, create a logger with logger = logging.getLogger(__name__). The logger is named after the module, so you can see where every message came from and silence noisy modules individually.
  • Call logging.basicConfig() once, at the start of the program (not inside library modules). Later calls do nothing if logging has already been configured, which surprises many people.
  • Pass values as arguments, logger.debug("x=%s", x), rather than formatting them yourself with an f-string. The message is then only built if it will actually be shown, which saves work for disabled DEBUG messages.
  • Inside an except block, use logger.exception(): it logs at ERROR level and appends the full traceback automatically.
import logging

logging.basicConfig(level=logging.INFO, format="%(levelname)s: %(message)s")
logger = logging.getLogger(__name__)

try:
    1 / 0
except ZeroDivisionError:
    logger.exception("Calculation failed")

ERROR: Calculation failed
Traceback (most recent call last):
  File "log_exc.py", line 7, in <module>
    1 / 0
    ~~^~~
ZeroDivisionError: division by zero
Calling logging.debug(...) directly on the module (instead of on a logger object) before basicConfig() silently configures logging with default settings. Your own basicConfig() call afterwards is then ignored. Configure logging first, then log.

Interactive Debugging with breakpoint() and pdb

Printing requires you to guess in advance which values matter, then re-run the program each time you guess wrong. An interactive debugger lets you pause the program at a chosen line and explore: inspect any variable, evaluate expressions, and step through the code one line at a time while watching what changes. Python's built-in debugger is pdb, and the easiest way to start it is to put a call to the built-in breakpoint() function where you want the program to stop.

The following program has a bug: a score of 70 should earn a "C", but it gets an "F". 
# grades.py
def letter_grade(score):
    if score >= 90:
        return "A"
    elif score >= 80:
        return "B"
    elif score > 70:
        return "C"
    return "F"


def report(scores):
    results = []
    for score in scores:
        breakpoint()              # execution pauses here on every loop
        results.append(letter_grade(score))
    return results


print(report([95, 70]))

(Pdb) p score > 70
False
(Pdb) q
Step by step: c continued to the second loop iteration, s stepped into letter_grade(), n moved line by line, w showed how we got here, and evaluating score > 70 revealed the bug: the condition should be score >= 70.

Essential pdb commands
Command Name What it does
n next Run the current line and stop at the next line in the same function (function calls on the line run without stopping inside them)
s step Run the current line, but stop inside any function it calls
c continue Resume normal execution until the next breakpoint (or the end)
l list Show the source code around the current line (ll shows the whole function)
p expr print Evaluate an expression and print its value (pp pretty-prints)
w where Show the call stack; the newest frame is at the bottom
q quit Abort the program and leave the debugger
Other handy commands: r (return: run until the current function returns), u / d (move up / down the call stack to inspect the caller's variables), b 12 (set a breakpoint at line 12), a (print the current function's arguments) and h (help). Pressing Enter on an empty line repeats the last command, which is convenient when stepping with n.

Controlling breakpoint()

breakpoint() is better than the older import pdb; pdb.set_trace() because it can be controlled from outside the code with the PYTHONBREAKPOINT environment variable. Setting it to 0 turns every breakpoint() call into a no-op, which is a useful safety net if one slips into code you run in production: 
> $env:PYTHONBREAKPOINT = "0"     # PowerShell
> python grades.py                # runs straight through without stopping
['A', 'F']
A variable whose name matches a pdb command, such as n, c or p, cannot be inspected by just typing its name: pdb runs the command instead. Use p n or prefix the line with ! (for example !c = 3) to make pdb treat it as Python code.
Leaving the debugger with q raises a bdb.BdbQuit exception to stop the program, so a traceback mentioning BdbQuit after quitting is normal. Remember to delete your breakpoint() calls once the bug is fixed. Editors such as VS Code and PyCharm offer the same features graphically: click in the margin to set a breakpoint and use the step buttons.
