Classes and Interfaces

Compose Classes Instead of Deeply Nesting Built-in Types

Dictionaries, lists and tuples are so convenient that it is tempting to keep adding layers to them: a dictionary of students, whose values are dictionaries of subjects, whose values are lists of (score, weight) tuples. Each layer seems harmless on its own, but after two or three levels the code becomes hard to read and fragile to change: every caller has to remember what data[name][subject][i][1] means.
Here is a gradebook that has started to grow out of control: 
grades = {}

def add_grade(student, subject, score, weight):
    grades.setdefault(student, {}).setdefault(subject, []).append((score, weight))

def average_grade(student):
    total, total_weight = 0, 0
    for subject_grades in grades[student].values():
        for score, weight in subject_grades:
            total += score * weight
            total_weight += weight
    return total / total_weight

add_grade("Alice", "Math", 90, 0.6)
add_grade("Alice", "Math", 80, 0.4)
add_grade("Alice", "Physics", 70, 1.0)
print(round(average_grade("Alice"), 2))  # 78.0
It works, but nothing in the data structure tells you what each level means. A good rule of thumb: as soon as you nest a dictionary inside a dictionary, or a tuple has more than two items, consider introducing small classes. Each class gets one clear responsibility and a name that documents it: 
from collections import defaultdict
from dataclasses import dataclass


@dataclass
class Grade:
    score: float
    weight: float


class Subject:
    def __init__(self):
        self._grades = []

    def report_grade(self, score, weight):
        self._grades.append(Grade(score, weight))

    def weighted_totals(self):
        total = sum(g.score * g.weight for g in self._grades)
        weight = sum(g.weight for g in self._grades)
        return total, weight


class Student:
    def __init__(self):
        self._subjects = defaultdict(Subject)

    def get_subject(self, name):
        return self._subjects[name]

    def average_grade(self):
        total, weight = 0, 0
        for subject in self._subjects.values():
            t, w = subject.weighted_totals()
            total += t
            weight += w
        return total / weight


class Gradebook:
    def __init__(self):
        self._students = defaultdict(Student)

    def get_student(self, name):
        return self._students[name]


book = Gradebook()
alice = book.get_student("Alice")
math = alice.get_subject("Math")
math.report_grade(90, 0.6)
math.report_grade(80, 0.4)
alice.get_subject("Physics").report_grade(70, 1.0)
print(round(alice.average_grade(), 2))  # 78.0
The refactored version is longer, but each piece is small, testable and easy to extend. If you later need to drop the lowest grade of each subject, the change lives inside Subject and no caller has to know about it.
Notice how defaultdict(Subject) passes the class itself as the factory: classes are callables, so calling Subject() creates the missing value on demand.
Things to Remember
  • Avoid dictionaries whose values are dictionaries, long tuples, or other deeply nested built-in types.
  • Use lightweight classes (often dataclasses) for small immutable or mutable records before you need a full class hierarchy.
  • When internal bookkeeping becomes complicated, split it into several classes that each own one level of the data.

Dataclasses

Many classes exist mainly to hold data. Writing their __init__, __repr__ and __eq__ by hand is repetitive and error prone. The @dataclass decorator from the dataclasses module reads the type-annotated class attributes and generates those methods for you. 
from dataclasses import dataclass


@dataclass
class Point:
    x: float
    y: float = 0.0  # fields with defaults must come after fields without


p = Point(3, 4)
print(p)                 # Point(x=3, y=4)
print(p == Point(3, 4))  # True  (generated __eq__ compares fields)
print(Point(1))          # Point(x=1, y=0.0)
p.x = 10                 # regular dataclasses are mutable
print(p.x)               # 10
The annotations are only used to discover the fields; Python does not check the types at runtime. Point("a", "b") works without complaint. Use a type checker such as mypy if you want those annotations enforced.

Mutable Defaults and field(default_factory=...)

A default value is shared by every instance, which is a classic bug with lists and dictionaries. Dataclasses protect you: a plain list, dict or set default raises a ValueError when the class is defined. Use field(default_factory=list) so a fresh object is created for each instance. field() also lets you exclude a field from the repr or from comparisons. 
from dataclasses import dataclass, field


@dataclass
class ShoppingCart:
    owner: str
    items: list[str] = field(default_factory=list)
    session_id: str = field(default="", repr=False, compare=False)


a = ShoppingCart("Alice")
b = ShoppingCart("Bob")
a.items.append("apple")
print(a)        # ShoppingCart(owner='Alice', items=['apple'])
print(b.items)  # []  each cart got its own list

from dataclasses import dataclass


@dataclass
class Broken:
    items: list = []
# ValueError: mutable default <class 'list'> for field items is not allowed: use default_factory

__post_init__ for Validation and Derived Fields

The generated __init__ calls __post_init__ (if you define it) after assigning the fields. It is the right place to validate input or compute derived values. Mark a computed attribute with field(init=False) so it is not a constructor argument. 
from dataclasses import dataclass, field


@dataclass
class Rectangle:
    width: float
    height: float
    area: float = field(init=False)

    def __post_init__(self):
        if self.width <= 0 or self.height <= 0:
            raise ValueError("sides must be positive")
        self.area = self.width * self.height


print(Rectangle(2, 3))  # Rectangle(width=2, height=3, area=6)

frozen=True and order=True

  • frozen=True makes instances immutable: assigning to a field raises FrozenInstanceError. Frozen dataclasses also get a __hash__, so they can be dictionary keys or set members. To "change" one, build a modified copy with dataclasses.replace().
  • order=True generates <, <=, > and >=. Instances are compared like tuples of their fields, in the order the fields are declared, so declare the most important sort key first.
from dataclasses import dataclass, replace, FrozenInstanceError


@dataclass(frozen=True, order=True)
class Version:
    major: int
    minor: int
    patch: int = 0


v1 = Version(1, 4)
v2 = Version(1, 10, 2)
print(v1 < v2)                  # True  compares (1, 4, 0) with (1, 10, 2)
print(sorted([v2, v1])[0])      # Version(major=1, minor=4, patch=0)
print({v1: "stable"}[Version(1, 4)])  # stable  (frozen instances are hashable)

try:
    v1.major = 2
except FrozenInstanceError as e:
    print(e)                    # cannot assign to field 'major'

v3 = replace(v1, patch=1)       # a new object; v1 is untouched
print(v3)                       # Version(major=1, minor=4, patch=1)
Other useful options: @dataclass(slots=True) (Python 3.10+) generates __slots__ for lower memory use, and kw_only=True forces callers to pass fields by keyword. dataclasses.asdict() converts an instance (recursively) into a dictionary.
frozen=True is shallow. A frozen dataclass holding a list still lets you append to that list. Use tuples or other immutable types inside frozen classes if you need true immutability.

namedtuple vs dataclass

Before dataclasses existed, collections.namedtuple (and its typed sibling typing.NamedTuple) was the usual way to create small record types. Both give you named fields, a readable repr and equality, but they are built on very different foundations. 
from typing import NamedTuple
from dataclasses import dataclass


class PointNT(NamedTuple):
    x: int
    y: int


@dataclass
class PointDC:
    x: int
    y: int


nt = PointNT(1, 2)
dc = PointDC(1, 2)

# A namedtuple IS a tuple: indexing, unpacking and len() all work
print(nt[0], len(nt))   # 1 2
x, y = nt
print(nt == (1, 2))     # True  -- equal to any tuple with the same values!

# A dataclass is a normal object
print(dc == PointDC(1, 2))  # True
print(dc == (1, 2))         # False
dc.x = 5                    # mutable by default
print(nt._replace(x=5))     # PointNT(x=5, y=2)  namedtuples are immutable
How to choose:
  • Use a namedtuple when the data really is a tuple: you want positional unpacking, you are replacing an existing tuple return value without breaking callers, or you need the very small memory footprint of a tuple.
  • Use a dataclass for almost everything else. It can be mutable or frozen, supports default_factory, __post_init__, ordering control, inheritance and methods naturally, and it will not accidentally compare equal to unrelated tuples.
Because a namedtuple is a sequence, callers can start relying on positional access like record[3]. Once they do, you can never reorder or insert fields without breaking them. That is a strong reason to prefer a dataclass for public APIs.

Accept Functions Instead of Classes for Simple Interfaces

In some languages, customising behaviour means implementing an interface class. Python is simpler: functions are first-class objects, so many APIs just accept a callable (a "hook"). You have already used hooks: the key argument of sorted() and the factory of defaultdict. 
from collections import defaultdict


def log_missing():
    print("Key added")
    return 0


counts = defaultdict(log_missing, {"green": 12})
counts["blue"] += 3   # prints: Key added
print(dict(counts))   # {'green': 12, 'blue': 3}
Hooks keep APIs decoupled: defaultdict knows nothing about logging, and log_missing knows nothing about dictionaries.
Sometimes the hook needs to remember state, such as how many keys were missing. You could use a closure with nonlocal, but a small class is often clearer. If you define the special method __call__, instances of the class can be called like functions, so they can be passed anywhere a function is expected. 
from collections import defaultdict


class CountMissing:
    def __init__(self):
        self.added = 0

    def __call__(self):
        self.added += 1
        return 0


counter = CountMissing()
current = {"green": 12, "blue": 3}
increments = [("red", 5), ("blue", 17), ("orange", 9)]

result = defaultdict(counter, current)  # counter is used like a function
for key, amount in increments:
    result[key] += amount

print(counter.added)       # 2  ('red' and 'orange' were missing)
print(callable(counter))   # True
The __call__ method signals clearly that the object's main purpose is to be used as a stateful function, and the state is easy to inspect afterwards (counter.added).
Write your own APIs this way too: accept a plain function for small hooks (on_error=print, key=len) rather than demanding that callers subclass something.

@classmethod as Alternative Constructors

Python only allows one __init__ per class, so how do you offer several ways to build an object (from a string, from a dict, from a file)? The idiomatic answer is a @classmethod. A class method receives the class itself as its first argument, conventionally named cls, instead of an instance. 
class Person:
    def __init__(self, name, birth_year):
        self.name = name
        self.birth_year = birth_year

    @classmethod
    def from_string(cls, text):
        name, year = text.split(",")
        return cls(name.strip(), int(year))

    @classmethod
    def from_dict(cls, data):
        return cls(data["name"], data["birth_year"])

    def age_in(self, year):
        return year - self.birth_year

    def __repr__(self):
        return f"{type(self).__name__}({self.name!r}, {self.birth_year})"


print(Person.from_string("Alice, 1990"))                    # Person('Alice', 1990)
print(Person.from_dict({"name": "Bob", "birth_year": 1985}))  # Person('Bob', 1985)

Why cls Matters: Subclasses Get the Constructors for Free

Because the method calls cls(...) rather than Person(...), it builds an instance of whichever class it was called on. Subclasses inherit working alternative constructors without rewriting them. The standard library uses this pattern everywhere: dict.fromkeys(), datetime.fromisoformat(), int.from_bytes(). 
class Person:
    def __init__(self, name, birth_year):
        self.name = name
        self.birth_year = birth_year

    @classmethod
    def from_string(cls, text):
        name, year = text.split(",")
        return cls(name.strip(), int(year))


class Employee(Person):
    pass


e = Employee.from_string("Carol, 1992")
print(type(e).__name__)  # Employee
Class methods also enable generic construction: code that receives a class object can create instances of it without knowing the concrete type, for example a function that takes reader_class and calls reader_class.from_config(config).
Use @staticmethod only for helpers that need neither the instance nor the class. If a method builds objects, make it a @classmethod so it cooperates with inheritance.

Initialize Parent Classes with super()

The old way to initialize a parent was to call it directly: Parent.__init__(self, ...). That works for simple single inheritance, but it breaks down with multiple inheritance. Consider a "diamond", where two classes inherit from the same base and a fourth class inherits from both: 
class Base:
    def __init__(self, value):
        print("Base.__init__")
        self.value = value


class TimesTwo(Base):
    def __init__(self, value):
        Base.__init__(self, value)
        self.value *= 2


class PlusFive(Base):
    def __init__(self, value):
        Base.__init__(self, value)
        self.value += 5


class Diamond(TimesTwo, PlusFive):
    def __init__(self, value):
        TimesTwo.__init__(self, value)
        PlusFive.__init__(self, value)


d = Diamond(5)
# Base.__init__
# Base.__init__
print(d.value)  # 10 -- expected (5 * 2) + 5 = 15!
Base.__init__ ran twice, and the second call reset value to 5, silently throwing away the doubling.
super() fixes this. It does not simply mean "my parent"; it means "the next class in the Method Resolution Order (MRO)". The MRO is a single, linear ordering of all the ancestors, computed with the C3 linearization algorithm, in which every class appears exactly once and each class comes before its parents. You can inspect it with ClassName.__mro__ or ClassName.mro(). 
class Base:
    def __init__(self, value):
        print("Base.__init__")
        self.value = value


class TimesTwo(Base):
    def __init__(self, value):
        super().__init__(value)
        self.value *= 2


class PlusFive(Base):
    def __init__(self, value):
        super().__init__(value)
        self.value += 5


class Diamond(TimesTwo, PlusFive):
    def __init__(self, value):
        super().__init__(value)


print([cls.__name__ for cls in Diamond.mro()])
# ['Diamond', 'TimesTwo', 'PlusFive', 'Base', 'object']

d = Diamond(5)  # Base.__init__ is printed only once
print(d.value)  # 20
Why 20 and not 15? Follow the MRO: Diamond calls super(), which is TimesTwo; TimesTwo calls super(), which (for a Diamond instance) is PlusFive, not Base! PlusFive then calls Base. The calls go down the MRO and the assignments run in reverse on the way back up: Base sets 5, PlusFive adds 5 (10), TimesTwo doubles it (20). The result depends on the order you list the base classes, which is exactly what the MRO documents.
Always call super().__init__(...) with no arguments to super itself. The zero-argument form (Python 3) automatically uses the current class and self, so renaming the class or changing the hierarchy never requires editing these calls.
For cooperative multiple inheritance, every class in the chain must call super(), and their __init__ signatures must be compatible (a common trick is to accept **kwargs and pass the rest along). A single class that calls its parent directly breaks the chain for everybody.

Mix-in Classes

A mix-in is a small class that provides a few extra methods for other classes to inherit, but which is not meant to be used on its own. A mix-in defines no __init__ and stores no instance attributes of its own; it relies only on what the host class already has. This avoids most of the complexity of multiple inheritance while letting you plug the same behaviour into unrelated classes.
The following mix-in converts any object into a dictionary by inspecting its __dict__ at runtime: 
import json


class ToDictMixin:
    def to_dict(self):
        return {key: self._convert(value) for key, value in self.__dict__.items()}

    def _convert(self, value):
        if isinstance(value, ToDictMixin):
            return value.to_dict()
        if isinstance(value, list):
            return [self._convert(v) for v in value]
        return value


class JsonMixin:
    def to_json(self):
        return json.dumps(self.to_dict())  # relies on to_dict() from the host


class Address(ToDictMixin):
    def __init__(self, city, zip_code):
        self.city = city
        self.zip_code = zip_code


class Customer(ToDictMixin, JsonMixin):
    def __init__(self, name, addresses):
        self.name = name
        self.addresses = addresses


c = Customer("Alice", [Address("Paris", "75001"), Address("Lyon", "69001")])
print(c.to_dict())
# {'name': 'Alice', 'addresses': [{'city': 'Paris', 'zip_code': '75001'}, {'city': 'Lyon', 'zip_code': '69001'}]}
print(c.to_json())
# {"name": "Alice", "addresses": [{"city": "Paris", "zip_code": "75001"}, {"city": "Lyon", "zip_code": "69001"}]}
Mix-ins compose: Customer gets both behaviours by listing both mix-ins. Because _convert is a normal method, a subclass can override it to customise how particular values are converted, which makes mix-ins easy to extend.
By convention, mix-in names end with Mixin, and mix-ins are listed before the main base class (e.g. class View(LoginRequiredMixin, BaseView)) so their methods take priority in the MRO.
If a mix-in starts needing its own __init__ and instance state, it is no longer a mix-in. Consider composition (holding a helper object as an attribute) instead.

Public vs Private Attributes

Python has no truly private attributes. Instead it relies on naming conventions:
  • name: public. Part of the class's interface.
  • _name: protected by convention. "Internal; use at your own risk." Nothing stops access, but tools and readers treat it as an implementation detail. from module import * also skips names that start with an underscore.
  • __name (two leading underscores, at most one trailing): name mangled. Inside a class body, Python rewrites it to _ClassName__name.
class Account:
    def __init__(self, balance):
        self.owner = "Alice"     # public
        self._history = []       # internal by convention
        self.__pin = 1234        # name-mangled


acct = Account(100)
print(acct._history)          # []  works, but you are touching internals
print(acct._Account__pin)     # 1234  the "private" name is just renamed
try:
    print(acct.__pin)
except AttributeError as e:
    print(e)                  # 'Account' object has no attribute '__pin'

What Name Mangling Is Really For

Name mangling is not a security feature. Its real purpose is to avoid accidental name clashes in subclasses. If a base class and a subclass both use an attribute called _value, the subclass silently overwrites the parent's data. With __value each class gets its own mangled name. 
class Parent:
    def __init__(self):
        self.__value = "parent's"

    def parent_value(self):
        return self.__value          # really self._Parent__value


class Child(Parent):
    def __init__(self):
        super().__init__()
        self.__value = "child's"     # really self._Child__value


c = Child()
print(c.parent_value())  # parent's  (no clash)
print(sorted(k for k in vars(c)))  # ['_Child__value', '_Parent__value']
In everyday code, prefer a single underscore. Double underscores make subclassing and debugging more awkward (subclasses cannot easily reach the attribute, and the mangled names are surprising). Reserve them for classes designed to be subclassed by people you don't control, where a clash is a real risk. Document protected attributes rather than trying to hide them: "we are all consenting adults here".
Names with two leading and two trailing underscores, such as __init__, are "dunder" special methods and are never mangled. Don't invent new dunder names of your own; they are reserved for Python.

Abstract Base Classes and Protocols

Sometimes you want to declare an interface: "anything that plays this role must provide these methods". Python offers two complementary tools: abstract base classes (nominal typing: you must inherit) and protocols (structural typing: you just need the right methods).

Abstract Base Classes with abc

Inherit from abc.ABC and decorate the required methods with @abstractmethod. Python then refuses to instantiate any class that has not implemented all of them, so mistakes surface at construction time rather than later when a missing method is first called. An ABC can also provide concrete helper methods that are built on top of the abstract ones. 
from abc import ABC, abstractmethod
import math


class Shape(ABC):
    @abstractmethod
    def area(self):
        """Return the area of the shape."""

    def describe(self):  # a concrete method shared by all shapes
        return f"{type(self).__name__} with area {self.area():.2f}"


class Circle(Shape):
    def __init__(self, r):
        self.r = r

    def area(self):
        return math.pi * self.r ** 2


class Square(Shape):
    def __init__(self, side):
        self.side = side
    # forgot to implement area()


print(Circle(1).describe())  # Circle with area 3.14
try:
    Square(2)
except TypeError as e:
    print(e)
# Can't instantiate abstract class Square without an implementation for abstract method 'area'
try:
    Shape()
except TypeError as e:
    print(e)
# Can't instantiate abstract class Shape without an implementation for abstract method 'area'

Protocols with typing.Protocol

Python culture favours duck typing: "if it has a read() method, treat it as a file". Requiring inheritance from your ABC can be too strict, especially for classes from third-party libraries you cannot modify. A typing.Protocol describes the required methods and any class that has them matches, without inheriting from anything. Protocols are mainly checked by static type checkers like mypy; adding @runtime_checkable also allows isinstance() checks. 
from typing import Protocol, runtime_checkable


@runtime_checkable
class SupportsClose(Protocol):
    def close(self) -> None: ...


class Connection:          # note: does NOT inherit from SupportsClose
    def close(self) -> None:
        print("connection closed")


class Logger:
    def close(self) -> None:
        print("logger closed")


def close_all(resources: list[SupportsClose]) -> None:
    for resource in resources:
        resource.close()


close_all([Connection(), Logger()])
# connection closed
# logger closed
print(isinstance(Connection(), SupportsClose))  # True
print(isinstance(42, SupportsClose))            # False
A runtime isinstance() check against a protocol only verifies that the methods exist; it does not check their signatures or return types. Rely on a static type checker for those guarantees.
Which one? Use an ABC when you own the hierarchy and want to share code and enforce implementation at instantiation time. Use a Protocol when you want to accept any object with the right shape, including classes you don't control.

Inheriting from collections.abc for Custom Containers

To make your own container, you could subclass list or dict directly. That works for simple additions, but the built-in types are implemented in C and their methods do not call each other: overriding __setitem__ in a dict subclass is ignored by update() and the constructor.
If you want a container whose behaviour is entirely yours, build it on the abstract base classes in collections.abc. Each ABC tells you which few methods you must implement and gives you the rest for free. For example, Sequence needs only __getitem__ and __len__, and then provides __contains__, __iter__, __reversed__, index() and count(). 
from collections.abc import Sequence


class BinaryNode:
    def __init__(self, value, left=None, right=None):
        self.value = value
        self.left = left
        self.right = right


class SequenceTree(Sequence):
    """Exposes a binary tree as an in-order sequence."""

    def __init__(self, root):
        self._values = list(self._walk(root))

    def _walk(self, node):
        if node is not None:
            yield from self._walk(node.left)
            yield node.value
            yield from self._walk(node.right)

    def __getitem__(self, index):
        return self._values[index]

    def __len__(self):
        return len(self._values)


tree = SequenceTree(BinaryNode(10, BinaryNode(5, BinaryNode(2)), BinaryNode(15)))
print(len(tree))          # 4
print(tree[1])            # 5
print(list(tree))         # [2, 5, 10, 15]   __iter__ comes from Sequence
print(15 in tree)         # True             __contains__ comes from Sequence
print(tree.index(10))     # 2                index() comes from Sequence
print(list(reversed(tree)))  # [15, 10, 5, 2]
The ABC also acts as a safety net: if you forget a required method, instantiation fails with a clear TypeError, just like with your own ABCs. 
from collections.abc import Sequence


class BadSequence(Sequence):
    def __getitem__(self, index):
        return index


BadSequence()
# TypeError: Can't instantiate abstract class BadSequence without an implementation for abstract method '__len__'
Other useful bases include Mapping / MutableMapping (implement __getitem__, __setitem__, __delitem__, __iter__, __len__ and get get(), keys(), update()... for free), Set, and Iterable. For a simple tweak to a dict, collections.UserDict is another option whose methods do call your overrides.
Things to Remember
  • Subclass built-in containers only for small additions that don't depend on overriding core methods.
  • Inherit from collections.abc to get a complete, consistent container interface from a handful of methods.
  • Your class also becomes recognisable to code that checks isinstance(obj, Sequence).
