Exceptions

Handling the ZeroDivisionError Exception

When something goes wrong while a program is running, Python creates a special object called an exception. If nothing in your code handles that exception, the program stops and Python prints a traceback: a report of where the error happened and what kind of error it was.
Dividing a number by zero is impossible, so Python raises a ZeroDivisionError: 
print(5 / 0)
# ZeroDivisionError: division by zero
The full traceback looks like this: 
Traceback (most recent call last):
  File "division_calculator.py", line 1, in <module>
    print(5 / 0)
          ~~^~~
ZeroDivisionError: division by zero
Read a traceback from the bottom up:
  • The last line gives the type of the exception (ZeroDivisionError) and a message explaining it.
  • The lines above show the file, the line number and the code that failed. Since Python 3.11 the ~~^~~ markers even point at the exact operation.
  • When the error happens inside a function, the traceback lists every call that led there, with the most recent call last.
Every exception type is a class, and its name tells you what went wrong. Knowing the name is what lets you write code that handles that specific problem.

Using try-except Blocks

When you know an error might happen, you can tell Python what to do instead of crashing. Put the code that might fail in a try block, and the code that should run if it fails in an except block naming the exception type:
  • If the try block runs without error, the except block is skipped.
  • If an error of the named type happens, Python stops running the try block at that line, jumps to the matching except block, and then continues with the rest of the program.
  • If a different type of error happens, the except block does not match and the program still crashes with a traceback.
try:
    print(5 / 0)
    print("This line is never reached.")
except ZeroDivisionError:
    print("You can't divide by zero!")

print("The program keeps running.")
# Output:
# You can't divide by zero!
# The program keeps running.
You can access the exception object itself with as. Converting it to a string gives the error message: 
try:
    number = int("forty-two")
except ValueError as error:
    print(f"Conversion failed: {error}")
    print(type(error).__name__)
# Output:
# Conversion failed: invalid literal for int() with base 10: 'forty-two'
# ValueError
Keep the try block as small as possible: only the lines that can actually raise the error you are handling. A large try block can accidentally catch errors from lines you did not expect to fail, hiding real bugs.

Using Exceptions to Prevent Crashes

Handling errors matters most when the program depends on things you do not control, such as user input, files or network connections. A crash is a bad experience for users: the work in progress is lost, and a traceback can reveal details about your code (file names, paths) that you may not want to show.
Here is a simple calculator that keeps asking for numbers. Without error handling, a single zero or a typo would end the program: 
print("Give me two numbers, and I'll divide them.")
print("Enter 'q' to quit.")

while True:
    first_number = input("\nFirst number: ")
    if first_number == 'q':
        break
    second_number = input("Second number: ")
    if second_number == 'q':
        break
    try:
        answer = float(first_number) / float(second_number)
    except ZeroDivisionError:
        print("You can't divide by 0!")
    except ValueError:
        print("Please enter numbers only.")
    else:
        print(answer)
# Example session:
# First number: 10
# Second number: 0
# You can't divide by 0!
#
# First number: 10
# Second number: abc
# Please enter numbers only.
#
# First number: 10
# Second number: 4
# 2.5
#
# First number: q
The program now survives bad input, explains the problem in plain language, and lets the user try again.

The else Block

A try statement can have an else block that runs only if the try block raised no exception. In the calculator above, print(answer) is in the else block because it only makes sense when the division succeeded.
Why not just put that code at the end of the try block? Because then any error it raises would also be caught by the except blocks, possibly with a misleading message. The else block keeps the try block focused on the one operation that may fail. The flow is:
  1. try: the code that might fail.
  2. except: runs if it failed with a matching exception.
  3. else: runs if it succeeded.
def safe_divide(a, b):
    try:
        result = a / b
    except ZeroDivisionError:
        print(f"Cannot divide {a} by zero.")
    else:
        print(f"{a} / {b} = {result}")

safe_divide(10, 4)  # 10 / 4 = 2.5
safe_divide(10, 0)  # Cannot divide 10 by zero.

Handling the FileNotFoundError Exception

Files are a classic source of errors: a file may have been moved, renamed, deleted, or the name may contain a typo. Trying to read a file that does not exist raises FileNotFoundError: 
with open('alice.txt', encoding='utf-8') as f:
    contents = f.read()
# FileNotFoundError: [Errno 2] No such file or directory: 'alice.txt'
The open() call is the line that fails, so it goes inside the try block. The work that depends on the file goes in else: 
filename = 'alice.txt'

try:
    with open(filename, encoding='utf-8') as f:
        contents = f.read()
except FileNotFoundError:
    print(f"Sorry, the file {filename} does not exist.")
else:
    words = contents.split()
    print(f"The file {filename} has about {len(words)} words.")
# Output (when alice.txt is missing):
# Sorry, the file alice.txt does not exist.
FileNotFoundError is one of several file-related errors that all inherit from OSError. Others you may meet are PermissionError (you are not allowed to read or write the file) and IsADirectoryError (the path is a folder). Catching OSError handles all of them.

Failing Silently

Sometimes you do not want to tell the user anything when an exception occurs; the program should simply carry on. The pass statement does nothing, and it can be used as the body of an except block.
In the example below, missing files are skipped without a message, so the output only lists the files that could be processed: 
def count_words(filename):
    """Count the approximate number of words in a file."""
    try:
        with open(filename, encoding='utf-8') as f:
            contents = f.read()
    except FileNotFoundError:
        pass
    else:
        print(f"The file {filename} has about {len(contents.split())} words.")

with open('poem.txt', 'w', encoding='utf-8') as f:
    f.write("Roses are red\nViolets are blue\n")

for name in ['poem.txt', 'missing.txt']:
    count_words(name)
# Output:
# The file poem.txt has about 6 words.
pass also acts as a placeholder that reminds you a decision was made to do nothing here. The contextlib.suppress helper (shown later) expresses the same idea more compactly.
Never silence errors you do not understand, and never write a bare except: with pass. It swallows every possible error, including typos in your own code, and makes bugs almost impossible to find. Always name the specific exception you expect.

Deciding Which Errors to Report

Whether to report an error, handle it quietly, or let the program crash depends on who uses the program and what the error means. Some guidelines:
  • Report errors the user can fix: a typo in a file name, a letter where a number was expected. Give a clear message that explains what to do.
  • Stay silent when the situation is expected and harmless: an optional configuration file that is not there yet, a cache that has to be rebuilt.
  • Let it crash (or re-raise) when the error is a bug in your code or when the program cannot continue in a meaningful way. Hiding it would only produce wrong results later.
  • Log errors in long-running programs or servers, so a developer can investigate them later even if the user only sees a short message.
A good error message says what went wrong and what the user can do about it. 
def load_settings(filename):
    """Settings are optional: fall back to defaults silently."""
    try:
        with open(filename, encoding='utf-8') as f:
            return f.read().splitlines()
    except FileNotFoundError:
        return ['theme=light']   # expected situation, nothing to report

def load_data(filename):
    """Data is required: tell the user exactly what is wrong."""
    try:
        with open(filename, encoding='utf-8') as f:
            return f.read()
    except FileNotFoundError:
        print(f"Could not find '{filename}'. Check the name and the folder, then try again.")
        return None

print(load_settings('settings.txt'))  # ['theme=light']
load_data('sales_2024.txt')
# Could not find 'sales_2024.txt'. Check the name and the folder, then try again.

The finally Block

A finally block runs no matter what: whether the try block succeeded, an exception was handled, an exception was not handled, or the function returned early. It is meant for clean-up work that must always happen, such as closing a connection, releasing a lock or printing a final status.
The complete form of the statement is try / except / else / finally, in that order. Only try is required, together with at least one except or a finally. 
def divide(a, b):
    try:
        result = a / b
    except ZeroDivisionError:
        print("  except: division by zero")
        return None
    else:
        print("  else: success")
        return result
    finally:
        print("  finally: always runs")

print(divide(10, 2))
print(divide(10, 0))
# Output:
#   else: success
#   finally: always runs
# 5.0
#   except: division by zero
#   finally: always runs
# None
Notice that finally runs even though both branches return: Python runs the clean-up first and then returns the value. If the exception is not handled at all, finally runs and then the exception continues to propagate: 
try:
    int("abc")
finally:
    print("Cleaning up before the crash.")
# Output:
# Cleaning up before the crash.
# ValueError: invalid literal for int() with base 10: 'abc'
Do not use return, break or continue inside finally. They silently discard any exception that was on its way out, so errors disappear without a trace.

Catching Multiple Exceptions

A single piece of code can fail in several ways. You have two options:
  • Several except blocks, when each error needs a different response. Python checks them from top to bottom and runs only the first one that matches.
  • One except with a tuple of exception types, when they should all be handled the same way.
def parse_and_invert(text):
    try:
        value = int(text)
        return 1 / value
    except ValueError:
        print(f"{text!r} is not a whole number.")
    except ZeroDivisionError:
        print("Zero has no inverse.")

print(parse_and_invert("4"))   # 0.25
parse_and_invert("four")       # 'four' is not a whole number.
parse_and_invert("0")          # Zero has no inverse.

def read_number(data, key):
    try:
        return int(data[key])
    except (KeyError, ValueError, TypeError) as error:
        print(f"Could not read {key!r}: {type(error).__name__}")
        return 0

record = {'age': '21', 'height': 'tall'}
print(read_number(record, 'age'))     # 21
read_number(record, 'height')         # Could not read 'height': ValueError
read_number(record, 'weight')         # Could not read 'weight': KeyError
Order matters: put specific exceptions before general ones. Because FileNotFoundError is a kind of OSError, an except OSError placed first would catch it, and a later except FileNotFoundError block would never run.

Raising Exceptions

Your own code can signal errors too, with the raise statement. This is the right thing to do when a function receives input it cannot work with. Raising an exception is better than returning a special value like None or -1, because the caller cannot accidentally ignore it: either they handle it, or the program stops and shows exactly where the problem is.
Choose the built-in exception that best describes the problem, and include a helpful message:
  • ValueError: the type is right but the value is not acceptable.
  • TypeError: the argument has the wrong type.
  • KeyError / IndexError: a key or index does not exist.
def set_age(age):
    if not isinstance(age, int):
        raise TypeError(f"age must be an int, not {type(age).__name__}")
    if age < 0 or age > 150:
        raise ValueError(f"age must be between 0 and 150, got {age}")
    return age

print(set_age(30))  # 30

try:
    set_age(-5)
except ValueError as error:
    print(error)    # age must be between 0 and 150, got -5

set_age("thirty")
# TypeError: age must be an int, not str

Re-raising an Exception

Sometimes you want to react to an error (for example, log it) but still let it continue to the caller, because you cannot actually fix it at this level. A bare raise inside an except block re-raises the current exception with its original traceback. 
def read_config(filename):
    try:
        with open(filename, encoding='utf-8') as f:
            return f.read()
    except FileNotFoundError:
        print(f"[log] config file {filename!r} is missing")
        raise   # pass the same exception on to the caller

try:
    read_config('app.cfg')
except FileNotFoundError:
    print("Using default configuration.")
# Output:
# [log] config file 'app.cfg' is missing
# Using default configuration.

Chaining with raise ... from

Often a low-level error should be turned into one that makes sense to the caller: a KeyError deep inside your code is less helpful than "unknown product code". raise NewError(...) from original raises the new exception and records the original as its cause. The traceback then shows both, joined by the line "The above exception was the direct cause of the following exception", so no information is lost.
Use from None to hide the original exception when it would only add noise. 
PRICES = {'A100': 9.99, 'B200': 24.50}

def get_price(code):
    try:
        return PRICES[code]
    except KeyError as error:
        raise ValueError(f"unknown product code: {code}") from error

try:
    get_price('Z999')
except ValueError as error:
    print(error)                  # unknown product code: Z999
    print(repr(error.__cause__))  # KeyError('Z999')

Custom Exceptions

For larger programs, it helps to define your own exception types. A custom exception is just a class that inherits from Exception (or from a more specific built-in exception). Benefits:
  • The name documents exactly what went wrong (InsufficientFundsError says more than ValueError).
  • Callers can catch your errors without accidentally catching unrelated ones.
  • The exception can carry extra data as attributes.
A common pattern is to create one base exception for your module or application and derive the specific errors from it, so callers can catch them all with a single except. By convention, exception names end in Error. 
class BankError(Exception):
    """Base class for all errors in the bank module."""

class InsufficientFundsError(BankError):
    def __init__(self, balance, amount):
        super().__init__(f"cannot withdraw {amount}, balance is only {balance}")
        self.balance = balance
        self.amount = amount

class AccountLockedError(BankError):
    pass

def withdraw(balance, amount, locked=False):
    if locked:
        raise AccountLockedError("this account is locked")
    if amount > balance:
        raise InsufficientFundsError(balance, amount)
    return balance - amount

try:
    withdraw(100, 250)
except InsufficientFundsError as error:
    print(error)                           # cannot withdraw 250, balance is only 100
    print(error.amount - error.balance)    # 150

try:
    withdraw(100, 10, locked=True)
except BankError as error:                 # catches every bank error
    print(f"{type(error).__name__}: {error}")  # AccountLockedError: this account is locked
If your __init__ takes custom arguments, call super().__init__(message) so the exception still has a readable message when it is printed or shown in a traceback.

The Exception Hierarchy

Built-in exceptions are organised as a family tree of classes. An except clause matches the named class and all its subclasses. Here is a small part of the tree: 
BaseException
 ├── SystemExit                 (raised by sys.exit())
 ├── KeyboardInterrupt          (the user pressed Ctrl+C)
 └── Exception                  (base of all "normal" errors)
      ├── ArithmeticError
      │    └── ZeroDivisionError
      ├── LookupError
      │    ├── IndexError
      │    └── KeyError
      ├── OSError
      │    ├── FileNotFoundError
      │    ├── FileExistsError
      │    └── PermissionError
      ├── TypeError
      └── ValueError
           └── UnicodeError

print(issubclass(FileNotFoundError, OSError))    # True
print(issubclass(KeyError, LookupError))         # True
print(issubclass(KeyboardInterrupt, Exception))  # False

try:
    [1, 2, 3][10]
except LookupError as error:   # catches both IndexError and KeyError
    print(type(error).__name__, '-', error)  # IndexError - list index out of range
Practical consequences:
  • except Exception catches almost everything but deliberately leaves out KeyboardInterrupt and SystemExit, so the user can still stop the program with Ctrl+C. Use it only at the top level of a program, for example to log unexpected errors before exiting.
  • A bare except: catches BaseException, which includes those two. Avoid it.
  • Custom exceptions should inherit from Exception, never directly from BaseException.

Context Managers and Exceptions

The with statement works with objects called context managers. A context manager runs set-up code when the block starts and clean-up code when it ends, even if an exception is raised inside the block. That is exactly what a try/finally would do, but packaged so you cannot forget it. File objects are context managers: the file is closed however the block ends. 
try:
    with open('data.txt', 'w', encoding='utf-8') as f:
        f.write('some data\n')
        raise RuntimeError('something failed mid-way')
except RuntimeError as error:
    print(error)       # something failed mid-way

print(f.closed)        # True: the with block closed the file despite the error

# The with block above is roughly equivalent to:
f = open('data.txt', 'w', encoding='utf-8')
try:
    f.write('some data\n')
finally:
    f.close()
with does not handle the exception; it only guarantees clean-up. The exception still propagates, which is why the example above still needs try/except around it.

Ignoring Errors with contextlib.suppress

contextlib.suppress is a context manager that silently ignores the exceptions you list. It is a compact, readable replacement for try/except/ pass. 
import os
from contextlib import suppress

with suppress(FileNotFoundError):
    os.remove('temporary_file.txt')   # no error if the file is already gone

print("Done.")  # Done.

Writing Your Own Context Manager

The @contextmanager decorator turns a generator function into a context manager. Code before yield is the set-up, the yielded value is what as receives, and code after yield is the clean-up. Putting the yield inside try/finally makes sure the clean-up runs even when the block raises an exception. 
import time
from contextlib import contextmanager

@contextmanager
def timer(label):
    start = time.perf_counter()
    print(f"[{label}] started")
    try:
        yield
    finally:
        elapsed = time.perf_counter() - start
        print(f"[{label}] finished in {elapsed:.2f} s")

with timer("sum"):
    total = sum(range(1_000_000))

try:
    with timer("division"):
        1 / 0
except ZeroDivisionError:
    print("Error handled, and the timer still reported.")
# Output (times will vary):
# [sum] started
# [sum] finished in 0.02 s
# [division] started
# [division] finished in 0.00 s
# Error handled, and the timer still reported.
Things to Remember
  • Catch specific exceptions, keep try blocks small, and put the code that depends on success in else.
  • Use finally or, better, a with statement for clean-up that must always happen.
  • Raise exceptions with clear messages when your function cannot do its job, and use raise ... from to keep the original cause.
  • Define custom exceptions that inherit from Exception, ideally from one base class per application.
  • Never silence errors with a bare except:.
