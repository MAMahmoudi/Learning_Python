Metaclasses and Attributes

Use Plain Attributes Instead of Getters and Setters

Programmers coming from Java or C++ often write explicit get_x() and set_x() methods for every attribute "just in case" they need extra logic later. In Python this is unnecessary and makes code noisy, especially for in-place operations: 
class OldResistor:
    def __init__(self, ohms):
        self._ohms = ohms

    def get_ohms(self):
        return self._ohms

    def set_ohms(self, ohms):
        self._ohms = ohms


r = OldResistor(50)
r.set_ohms(r.get_ohms() + 5)   # clumsy
print(r.get_ohms())            # 55
The Pythonic approach is to start with plain public attributes: 
class Resistor:
    def __init__(self, ohms):
        self.ohms = ohms
        self.voltage = 0
        self.current = 0


r = Resistor(50)
r.ohms += 5      # natural and readable
print(r.ohms)    # 55
Why is this safe? Because if you later need validation or computed values, you can turn the attribute into a @property (next section) without changing a single caller: r.ohms keeps working exactly the same way. Python lets you start simple and add behaviour later, so you never pay the cost of getters and setters up front.

@property

The @property decorator turns a method into something that looks like an attribute. Reading the attribute calls the getter; adding @name.setter lets you intercept assignments. Typical uses:
  • Validation: reject bad values the moment they are assigned.
  • Read-only attributes: define a getter without a setter.
  • Computed attributes: values derived from other attributes, always up to date.
class Temperature:
    def __init__(self, celsius):
        self.celsius = celsius   # goes through the setter, so it is validated too

    @property
    def celsius(self):
        return self._celsius

    @celsius.setter
    def celsius(self, value):
        if value < -273.15:
            raise ValueError("below absolute zero")
        self._celsius = value

    @property
    def fahrenheit(self):        # computed, read-only
        return self._celsius * 9 / 5 + 32


t = Temperature(25)
print(t.fahrenheit)   # 77.0
t.celsius = 100
print(t.fahrenheit)   # 212.0
try:
    t.celsius = -300
except ValueError as e:
    print(e)          # below absolute zero
try:
    t.fahrenheit = 50
except AttributeError as e:
    print(e)          # property 'fahrenheit' of 'Temperature' object has no setter
Notice that the value is stored under a different name, _celsius. If the setter assigned self.celsius = value, it would call itself again and again until Python raised a RecursionError.

Caching an Expensive Computed Value

If a computed property is expensive and its inputs never change, functools.cached_property computes it once on first access and then stores the result in the instance. 
from functools import cached_property


class Dataset:
    def __init__(self, values):
        self.values = values

    @cached_property
    def total(self):
        print("computing...")
        return sum(self.values)


d = Dataset([1, 2, 3])
print(d.total)  # computing...  then 6
print(d.total)  # 6  (no recomputation)
Follow the "rule of least surprise": property getters should be fast and free of side effects. Callers expect obj.x to behave like a cheap attribute lookup. If an operation is slow (database queries, network I/O) or changes other state, make it a normal method so its cost is visible at the call site.

Descriptors for Reusable @property Logic

A property's logic is tied to a single attribute. If an Exam class needs the same 0–100 validation for math, physics and writing, you would have to copy the property three times. A descriptor packages that logic in a reusable class.
A descriptor is any object, stored as a class attribute, that defines __get__, __set__ or __delete__. When you access the attribute through an instance, Python calls those methods instead of reading the instance dictionary. (property, classmethod and even ordinary methods are all implemented with descriptors.)
The special method __set_name__(self, owner, name) is called automatically when the class is created, telling the descriptor which attribute name it was assigned to. 
class Grade:
    def __set_name__(self, owner, name):
        self.public_name = name
        self.private_name = "_" + name   # where each instance stores its value

    def __get__(self, instance, owner):
        if instance is None:             # accessed on the class: Exam.math
            return self
        return getattr(instance, self.private_name)

    def __set__(self, instance, value):
        if not 0 <= value <= 100:
            raise ValueError(f"{self.public_name} must be between 0 and 100")
        setattr(instance, self.private_name, value)


class Exam:
    math = Grade()
    physics = Grade()
    writing = Grade()

    def __init__(self, math, physics, writing):
        self.math = math
        self.physics = physics
        self.writing = writing


first = Exam(90, 75, 60)
second = Exam(40, 85, 99)
print(first.math, second.math)  # 90 40   each instance keeps its own value
print(vars(first))              # {'_math': 90, '_physics': 75, '_writing': 60}
try:
    first.physics = 120
except ValueError as e:
    print(e)                    # physics must be between 0 and 100

Pitfall: Storing Values on the Descriptor

There is only one descriptor object per class attribute, shared by every instance. If you store the value on the descriptor itself (self.value = value), all instances overwrite each other: 
class BrokenGrade:
    def __get__(self, instance, owner):
        return self.value

    def __set__(self, instance, value):
        self.value = value  # stored on the shared descriptor!


class Exam:
    math = BrokenGrade()


first = Exam()
first.math = 90
second = Exam()
second.math = 40
print(first.math)  # 40 -- first's grade was overwritten
Storing the data in the instance (as in Grade above, under a name derived in __set_name__) solves this. An alternative is a weakref.WeakKeyDictionary keyed by instance, but per-instance storage is simpler and does not require the instances to be hashable.

__getattr__, __getattribute__ and __setattr__

Python lets a class hook into attribute access itself, which is how proxies, lazy loaders and ORMs are built. There are three hooks, and the difference between them is crucial:
  • __getattr__(self, name) is called only when normal lookup fails (the attribute is not in the instance, its class or its parents).
  • __getattribute__(self, name) is called on every attribute access, even for attributes that exist.
  • __setattr__(self, name, value) is called on every attribute assignment.

Lazy Attributes with __getattr__

Because __getattr__ only runs for missing attributes, it is perfect for computing or loading a value on demand. If you store the result with setattr, the next lookup finds it normally and __getattr__ is not called again. 
class LazyRecord:
    def __init__(self):
        self.exists = 5

    def __getattr__(self, name):
        print(f"* __getattr__({name!r}) computing value")
        value = f"Value for {name}"
        setattr(self, name, value)   # cache it in the instance dict
        return value


data = LazyRecord()
print(data.exists)  # 5   (normal lookup, no hook)
print(data.foo)
# * __getattr__('foo') computing value
# Value for foo
print(data.foo)     # Value for foo   (found normally this time)

Intercepting Every Access with __getattribute__

__getattribute__ runs every time, which makes it useful for checks that must always happen (logging, checking whether a database transaction is still open). The catch: inside it, any self.something calls __getattribute__ again. To reach the real attribute, delegate to super().__getattribute__(name). 
class LoggingRecord:
    def __init__(self):
        self.exists = 5

    def __getattribute__(self, name):
        print(f"* __getattribute__({name!r})")
        return super().__getattribute__(name)   # the safe way to read


data = LoggingRecord()
print(data.exists)
# * __getattribute__('exists')
# 5
print(data.exists)
# * __getattribute__('exists')
# 5
Accessing self._data inside __getattribute__ or assigning self.x = ... inside __setattr__ calls the same hook recursively and ends in a RecursionError. Always go through super().__getattribute__() / super().__setattr__() (or object.__getattribute__(self, ...)) inside these methods.
class BrokenRecord:
    def __init__(self, data):
        self._data = data

    def __getattribute__(self, name):
        return self._data[name]   # self._data calls __getattribute__ again!


BrokenRecord({"foo": 3}).foo
# RecursionError: maximum recursion depth exceeded

Watching Assignments with __setattr__

class SavingRecord:
    def __setattr__(self, name, value):
        print(f"* saving {name} = {value!r}")   # e.g. write to a database here
        super().__setattr__(name, value)        # actually store it


r = SavingRecord()
r.score = 10       # * saving score = 10
r.score += 5       # * saving score = 15
print(r.score)     # 15
hasattr() and getattr(obj, name, default) also trigger these hooks. If your __getattr__ should signal "not found", it must raise AttributeError (not KeyError), otherwise hasattr() and default values stop working.

__slots__

Normally every instance stores its attributes in its own dictionary, __dict__. Dictionaries are flexible but use a fair amount of memory. Declaring __slots__ tells Python the fixed list of attributes an instance may have; it then stores them in a compact array and creates no __dict__. Benefits:
  • Noticeably less memory per instance, which matters when you create millions of small objects.
  • Slightly faster attribute access.
  • Typos in attribute names raise an error instead of silently creating a new attribute.
class Point:
    __slots__ = ("x", "y")

    def __init__(self, x, y):
        self.x = x
        self.y = y


p = Point(1, 2)
p.x = 10                       # fine: 'x' is a declared slot
print(hasattr(p, "__dict__"))  # False
try:
    p.z = 3                    # not declared
except AttributeError as e:
    print(e)                   # 'Point' object has no attribute 'z'

Pitfalls

  • Inheritance: a subclass that does not define its own __slots__ gets a __dict__ again, losing the memory savings. Each class in the hierarchy should declare only its new slots.
  • A slot cannot also have a class-level default value with the same name (x = 0 next to __slots__ = ("x",) raises a ValueError). Set defaults in __init__ instead.
  • Instances without __dict__ can't be given arbitrary attributes, which breaks some tools (e.g. functools.cached_property). Add "__weakref__" to the slots if you need weak references.
class Point:
    __slots__ = ("x", "y")


class Point3D(Point):
    __slots__ = ("z",)        # only the new attribute


class LoosePoint(Point):
    pass                      # no __slots__: gets a __dict__ again


print(hasattr(Point3D(), "__dict__"))     # False
print(hasattr(LoosePoint(), "__dict__"))  # True
With a dataclass, simply write @dataclass(slots=True) and the slots are generated from the fields.

Validate Subclasses with __init_subclass__

Sometimes a base class needs to check that every subclass is defined correctly: a required class attribute is present, a value is in range, and so on. Checking in __init__ would only catch mistakes when an object is created, possibly long after the program started.
The __init_subclass__ class method is called automatically every time a subclass is defined, receiving the new subclass as cls. Errors are raised as soon as the module containing the bad class is imported. 
class Polygon:
    sides = None  # every subclass must override this

    def __init_subclass__(cls, **kwargs):
        super().__init_subclass__(**kwargs)
        if cls.sides is None or cls.sides < 3:
            raise ValueError(f"{cls.__name__}: polygons need 3 or more sides")

    @classmethod
    def interior_angles(cls):
        return (cls.sides - 2) * 180


class Triangle(Polygon):
    sides = 3


class Hexagon(Polygon):
    sides = 6


print(Triangle.interior_angles())  # 180
print(Hexagon.interior_angles())   # 720

try:
    class Line(Polygon):           # fails at class definition time
        sides = 2
except ValueError as e:
    print(e)                       # Line: polygons need 3 or more sides

Class Keyword Arguments

Extra keyword arguments in the class statement are passed to __init_subclass__, which makes configuring subclasses very readable: 
class Filled:
    def __init_subclass__(cls, color="black", **kwargs):
        super().__init_subclass__(**kwargs)
        if color not in {"red", "green", "blue", "black"}:
            raise ValueError(f"unsupported color: {color}")
        cls.color = color


class RedSquare(Filled, color="red"):
    pass


print(RedSquare.color)  # red
Always call super().__init_subclass__(**kwargs). If several base classes (for example two mix-ins) each define __init_subclass__, this call is what lets all of them run, just like cooperative __init__ with super().

Register Classes with __init_subclass__

Another common need is a registry: a mapping from names to classes, used by plugin systems, serializers, command dispatchers and so on. The danger with manual registration (register(MyClass) after each class) is forgetting it; the program then fails much later, far from the cause. Doing the registration in __init_subclass__ makes it impossible to forget: simply inheriting from the base class registers the subclass. 
import json

REGISTRY = {}


class Serializable:
    def __init_subclass__(cls, **kwargs):
        super().__init_subclass__(**kwargs)
        REGISTRY[cls.__name__] = cls

    def __init__(self, *args):
        self.args = args

    def serialize(self):
        return json.dumps({"class": type(self).__name__, "args": self.args})

    def __repr__(self):
        return f"{type(self).__name__}{self.args}"


def deserialize(data):
    params = json.loads(data)
    cls = REGISTRY[params["class"]]   # look up the right class by name
    return cls(*params["args"])


class Point2D(Serializable):
    pass


class Vector3D(Serializable):
    pass


print(sorted(REGISTRY))  # ['Point2D', 'Vector3D']
text = Vector3D(1, 2, 3).serialize()
print(text)              # {"class": "Vector3D", "args": [1, 2, 3]}
print(deserialize(text)) # Vector3D(1, 2, 3)
The registry could also live on the base class itself (e.g. Serializable.registry), which keeps related plugins grouped and avoids a global variable. Use a key other than __name__ (a class keyword such as name="point") if two modules might define classes with the same name.

Class Decorators

A class decorator is a function that receives a class object right after the class statement finishes, and returns a class (usually the same one, modified). The syntax @decorator above class C: is just shorthand for C = decorator(C). You already know one: @dataclass.
Class decorators are ideal when you want to apply the same change to every method of a class, or to opt specific classes into a behaviour without forcing an inheritance relationship. Here is a decorator that adds logging to every method: 
import functools
import types


def trace_func(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        result = func(*args, **kwargs)
        print(f"{func.__name__}{args[1:]} -> {result!r}")
        return result
    return wrapper


def trace_methods(cls):
    for name, value in list(vars(cls).items()):
        if isinstance(value, types.FunctionType) and not name.startswith("__"):
            setattr(cls, name, trace_func(value))
    return cls


@trace_methods
class Calculator:
    def add(self, a, b):
        return a + b

    def scale(self, a, factor=2):
        return a * factor


calc = Calculator()
calc.add(2, 3)     # add(2, 3) -> 5
calc.scale(4)      # scale(4,) -> 8
Class decorators also make registration explicit and opt-in, without a shared base class: 
COMMANDS = {}


def command(name):
    def decorator(cls):
        COMMANDS[name] = cls
        return cls        # always return the class!
    return decorator


@command("greet")
class Greet:
    def run(self):
        return "Hello!"


print(COMMANDS["greet"]().run())  # Hello!
A class decorator that forgets return cls returns None, and the class name in your module silently becomes None. Also remember that a decorator only affects the class it decorates; unlike __init_subclass__ or a metaclass, it is not inherited by subclasses.

Metaclasses

In Python, classes are objects too, and every object has a type. The type of a class is its metaclass. By default that is type: 
class Dog:
    sound = "woof"


print(type(Dog()))   # <class '__main__.Dog'>
print(type(Dog))     # <class 'type'>
print(type(type))    # <class 'type'>

# A class statement is roughly equivalent to calling type(name, bases, namespace)
Cat = type("Cat", (), {"sound": "meow", "speak": lambda self: self.sound})
print(Cat().speak())  # meow
When Python executes a class statement, it runs the body to build a namespace dictionary and then calls the metaclass with (name, bases, namespace) to create the class object. A custom metaclass is a subclass of type that overrides __new__ (or __init__) to inspect or modify classes as they are created. Because the metaclass is inherited, it applies to every subclass too.

A Simple Metaclass

This metaclass enforces a naming rule on every class that uses it and records the creation of each one: 
class LowercaseMethodsMeta(type):
    def __new__(meta, name, bases, namespace, **kwargs):
        for attr, value in namespace.items():
            if callable(value) and not attr.startswith("__") and attr != attr.lower():
                raise TypeError(f"{name}.{attr}: method names must be lowercase")
        cls = super().__new__(meta, name, bases, namespace, **kwargs)
        print(f"created class {name}")
        return cls


class Model(metaclass=LowercaseMethodsMeta):
    def save(self):
        return "saved"


class User(Model):           # the metaclass is inherited
    def get_name(self):
        return "alice"
# Output:
# created class Model
# created class User

try:
    class Bad(Model):
        def GetName(self):
            return "oops"
except TypeError as e:
    print(e)                 # Bad.GetName: method names must be lowercase

Prefer Simpler Tools When You Can

The same check could be written with __init_subclass__ in fewer lines, and it would be easier for readers to follow. Metaclasses have real drawbacks:
  • They are harder to understand and debug than ordinary methods.
  • A class can have only one metaclass. Combining two base classes with unrelated metaclasses raises a TypeError ("metaclass conflict"), which often bites when mixing frameworks or combining with abc.ABC (whose metaclass is ABCMeta).
class MetaA(type):
    pass


class MetaB(type):
    pass


class A(metaclass=MetaA):
    pass


class B(metaclass=MetaB):
    pass


class C(A, B):
    pass
# TypeError: metaclass conflict: the metaclass of a derived class must be a (non-strict) subclass of the metaclasses of all its bases
A practical decision guide:
  • Need to validate or register subclasses? Use __init_subclass__.
  • Need to modify one specific class (wrap its methods, add generated methods)? Use a class decorator.
  • Need per-attribute behaviour? Use @property or a descriptor with __set_name__.
  • Reach for a metaclass only when you must control class creation itself, e.g. customising the namespace with __prepare__, changing how the class object behaves (len(MyEnum), MyEnum["RED"] in the enum module), or building a framework like an ORM.
"Metaclasses are deeper magic than 99% of users should ever worry about." If you are not sure you need one, you almost certainly don't.
