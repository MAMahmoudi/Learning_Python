Functions

Returning Multiple Values

A Python function always returns exactly one object. When you write return a, b, Python quietly builds a tuple (a, b) and returns that. The caller can then use unpacking to split the tuple back into separate variables. This makes it feel as if the function returned several values at once. 
def min_max(numbers):
    return min(numbers), max(numbers)   # really returns one tuple

result = min_max([7, 2, 9, 4])
print(result)          # (2, 9)
print(type(result))    # <class 'tuple'>

lowest, highest = min_max([7, 2, 9, 4])   # unpack the tuple
print(lowest, highest)  # 2 9
Starred expressions (covered in the Lists and Dictionaries chapter) work here too, which is handy when a function returns a sequence and you only care about some parts of it: 
def ranked(scores):
    return sorted(scores, reverse=True)

first, second, *others = ranked([55, 91, 78, 64, 88])
print(first, second)  # 91 88
print(others)         # [78, 64, 55]

Don't unpack more than three values

Returning many values in a tuple quickly becomes fragile. The caller must remember the exact order of the values, and since they are often all numbers, swapping two of them produces no error, only wrong results that are hard to spot. Long unpacking lines are also hard to read.
A good rule: if a function returns more than three values, return a small object with named fields instead, such as a NamedTuple or a dataclass. 
# Hard to use correctly: which position is which?
def describe(numbers):
    count = len(numbers)
    total = sum(numbers)
    return count, total, total / count, min(numbers), max(numbers)

count, average, total, low, high = describe([3, 5, 10])  # oops: average and total swapped!
print(average)  # 18  (this is actually the total)

from typing import NamedTuple

class Stats(NamedTuple):
    count: int
    total: float
    average: float
    low: float
    high: float

def describe(numbers):
    count = len(numbers)
    total = sum(numbers)
    return Stats(count, total, total / count, min(numbers), max(numbers))

stats = describe([3, 5, 10])
print(stats.average)  # 6.0
print(stats.high)     # 10
print(stats)          # Stats(count=3, total=18, average=6.0, low=3, high=10)
low, high = stats.low, stats.high   # read only the fields you need
A NamedTuple is still a tuple, so old code that unpacks it positionally keeps working, while new code can use the clearer attribute names.

Prefer Raising Exceptions to Returning None

When a function cannot produce a valid result, it is tempting to return None as a "special" value. The problem is that None, 0, "" and empty containers are all falsy. A caller who checks the result with a simple if not result: cannot tell the difference between "it failed" and "it worked and the answer is zero". 
def careful_divide(a, b):
    try:
        return a / b
    except ZeroDivisionError:
        return None

result = careful_divide(0, 5)    # a perfectly valid answer: 0.0
if not result:
    print("Invalid inputs")      # Wrongly printed! 0.0 is falsy too.
The better approach is to raise an exception and document it. Now the caller is forced to deal with the error case explicitly, and a valid result of 0.0 can never be mistaken for a failure. Type hints make the contract even clearer: the function returns a float, never None. 
def careful_divide(a: float, b: float) -> float:
    """Divide a by b.

    Raises:
        ValueError: if b is zero.
    """
    try:
        return a / b
    except ZeroDivisionError as e:
        raise ValueError("Invalid inputs: cannot divide by zero") from e

try:
    result = careful_divide(10, 0)
except ValueError as error:
    print(error)                 # Invalid inputs: cannot divide by zero
else:
    print(f"Result is {result:.1f}")

print(careful_divide(0, 5))      # 0.0
Returning None is fine when "nothing" is a normal, expected answer, like dict.get() for a missing key. Raise an exception when the situation is truly an error the caller must handle.

Closures and Variable Scope

When Python looks up a name, it searches four scopes in order, known as the LEGB rule:
  1. Local: names assigned inside the current function.
  2. Enclosing: names in any outer function that contains the current one.
  3. Global: names defined at the top level of the module.
  4. Built-in: names Python provides, like len and print.
If the name is not found anywhere, a NameError is raised. 
x = "global"

def outer():
    x = "enclosing"
    def inner():
        print(x)        # not local, so Python finds it in the enclosing scope
    inner()

outer()                 # enclosing
print(len("abc"))       # 3  (len comes from the built-in scope)
A closure is an inner function that remembers variables from the enclosing function, even after the outer function has finished running. This lets you create small, configurable functions on the fly: 
def make_multiplier(factor):
    def multiply(value):
        return value * factor    # 'factor' is remembered by the closure
    return multiply

double = make_multiplier(2)
triple = make_multiplier(3)
print(double(10))  # 20
print(triple(10))  # 30
Closures are also useful as key functions. Here a closure sorts a list so that "priority" items come first, and also records whether any of them were seen: 
def sort_priority(values, group):
    found = False
    def helper(x):
        if x in group:
            found = True        # BUG: this creates a NEW local variable
            return (0, x)
        return (1, x)
    values.sort(key=helper)
    return found

numbers = [8, 3, 1, 2, 5, 4, 7, 6]
print(sort_priority(numbers, {2, 3, 5, 7}))  # False  (expected True!)
print(numbers)                               # [2, 3, 5, 7, 1, 4, 6, 8]
The sorting worked, but found is still False. Why? Reading a variable follows the LEGB rule, but assigning to a variable inside a function always makes it local to that function, unless you say otherwise. So found = True created a separate local found inside helper.
The nonlocal statement tells Python that assignments should go to the variable in the enclosing scope: 
def sort_priority(values, group):
    found = False
    def helper(x):
        nonlocal found          # assign to the enclosing 'found'
        if x in group:
            found = True
            return (0, x)
        return (1, x)
    values.sort(key=helper)
    return found

numbers = [8, 3, 1, 2, 5, 4, 7, 6]
print(sort_priority(numbers, {2, 3, 5, 7}))  # True
Similarly, the global statement lets a function assign to a module-level variable. Both should be used sparingly: in long functions it gets hard to follow where a variable is being changed. If your state becomes complex, wrap it in a small class with a __call__ method instead. 
class Sorter:
    def __init__(self, group):
        self.group = group
        self.found = False

    def __call__(self, x):
        if x in self.group:
            self.found = True
            return (0, x)
        return (1, x)

sorter = Sorter({2, 3, 5, 7})
numbers = [8, 3, 1, 2, 5, 4, 7, 6]
numbers.sort(key=sorter)
print(sorter.found)  # True
print(numbers)       # [2, 3, 5, 7, 1, 4, 6, 8]
Closures capture variables, not values. Functions created in a loop all see the loop variable's final value: [lambda: i for i in range(3)] gives three functions that all return 2. Use a default argument (lambda i=i: i) to capture the current value.

Variable Positional Arguments (*args)

Putting * before a parameter name lets a function accept any number of positional arguments. Inside the function, they arrive packed in a tuple. By convention this parameter is called *args, but a descriptive name is often better. This removes noise for callers: they no longer need to wrap values in a list. 
def log(message, *values):
    if not values:
        print(message)
    else:
        values_str = ", ".join(str(v) for v in values)
        print(f"{message}: {values_str}")

log("My numbers are", 1, 2)   # My numbers are: 1, 2
log("Hi there")               # Hi there
If you already have a sequence, put * in front of it in the call to spread its items out as separate positional arguments: 
def log(message, *values):
    print(message, values)

favorites = [7, 33, 99]
log("Favorite colors", *favorites)   # Favorite colors (7, 33, 99)

Pitfalls of *args

  1. Everything is converted to a tuple first. If a caller passes a generator with *, Python must consume the whole generator to build the tuple. For a huge or infinite generator this can use a lot of memory or never finish. Only use *args when you expect a small number of inputs.
  2. Adding new positional parameters later is risky. Old calls will shift their arguments into the wrong parameter without any error.
def my_generator():
    for i in range(5):
        yield i

def show(*args):
    print(args)

show(*my_generator())  # (0, 1, 2, 3, 4)  the whole generator was consumed

# Version 2 adds a 'sequence' parameter before *values
def log(sequence, message, *values):
    if not values:
        print(f"{sequence} - {message}")
    else:
        values_str = ", ".join(str(v) for v in values)
        print(f"{sequence} - {message}: {values_str}")

log(1, "Favorites", 7, 33)    # 1 - Favorites: 7, 33   (new style call, correct)
log("Favorite numbers", 7, 33)  # Favorite numbers - 7: 33   (old style call, silently wrong!)
To extend a function that takes *args safely, add new options as keyword-only arguments (see below) instead of new positional parameters.

Keyword Arguments and Default Values

Any Python function can be called with arguments passed by keyword, name=value, in any order. Keyword arguments must come after all positional ones, and each parameter can be given only once. 
def remainder(number, divisor):
    return number % divisor

print(remainder(20, 7))                 # 6
print(remainder(20, divisor=7))         # 6
print(remainder(number=20, divisor=7))  # 6
print(remainder(divisor=7, number=20))  # 6

def remainder(number, divisor):
    return number % divisor

remainder(number=20, 7)
# SyntaxError: positional argument follows keyword argument

def remainder(number, divisor):
    return number % divisor

remainder(20, number=7)
# TypeError: remainder() got multiple values for argument 'number'
Keyword arguments give three main benefits:
  1. Clarity: connect(timeout=5) is much easier to read than connect(5).
  2. Default values: parameters with defaults can be skipped, so the common case stays short.
  3. Backward compatibility: you can add new parameters with defaults without breaking existing callers.
def flow_rate(weight_diff, time_diff, period=1, units_per_kg=1):
    return (weight_diff * units_per_kg) / time_diff * period

weight_diff = 0.5
time_diff = 3
print(flow_rate(weight_diff, time_diff))                    # 0.16666666666666666 (kg per second)
print(flow_rate(weight_diff, time_diff, period=3600))       # 600.0 (kg per hour)
print(flow_rate(weight_diff, time_diff, units_per_kg=2.2))  # 0.3666666666666667 (pounds per second)
The ** operator works for keywords the way * works for positions. In a call, **my_dict passes each key as a keyword argument. In a definition, **kwargs collects any extra keyword arguments into a dictionary. 
def remainder(number, divisor):
    return number % divisor

my_kwargs = {"number": 20, "divisor": 7}
print(remainder(**my_kwargs))  # 6

def print_parameters(**kwargs):
    for key, value in kwargs.items():
        print(f"{key} = {value}")

print_parameters(alpha=1.5, beta=9, gamma=4)
# Output:
# alpha = 1.5
# beta = 9
# gamma = 4

Using None for Dynamic Default Arguments

A default argument value is evaluated only once: when the def statement runs (usually when the module is loaded), not each time the function is called. This surprises people when the default should be "fresh" on every call. 
from datetime import datetime
from time import sleep

def log(message, when=datetime.now()):   # evaluated once, at definition time!
    print(f"{when:%H:%M:%S.%f}: {message}")

log("Hi there!")
sleep(0.1)
log("Hello again!")   # prints the SAME timestamp as the first call
The fix is to use None as the default and compute the real value inside the function body, where it runs on every call. Document this behaviour in the docstring. 
from datetime import datetime

def log(message, when=None):
    """Log a message with a timestamp.

    Args:
        message: Message to print.
        when: datetime of when the message occurred.
            Defaults to the present time.
    """
    if when is None:
        when = datetime.now()
    print(f"{when:%H:%M:%S.%f}: {message}")

The mutable default pitfall

Because the default is created only once, a mutable default such as a list or dictionary is shared by every call that uses it. Changes made during one call are still there in the next one. 
def add_item(item, basket=[]):     # one list shared by all calls!
    basket.append(item)
    return basket

first = add_item("apple")
second = add_item("banana")
print(first)            # ['apple', 'banana']
print(second)           # ['apple', 'banana']
print(first is second)  # True  (both are the same default list)

def add_item(item, basket=None):
    if basket is None:
        basket = []                # a brand-new list on every call
    basket.append(item)
    return basket

first = add_item("apple")
second = add_item("banana")
print(first)   # ['apple']
print(second)  # ['banana']
Never use a mutable object ([], {}, set(), or an instance of your own class) as a default argument value. Use None and create the object inside the function. Linters such as Pylint and Ruff will warn you about this mistake.

Keyword-Only and Positional-Only Arguments

Some arguments are easy to confuse when passed by position, especially boolean flags. Look at this call: safe_division(1, 0, False, True). Which flag is which? It is impossible to tell without reading the function definition.
Python lets you control how each argument may be passed using two special markers in the parameter list:
  • Parameters after a bare * are keyword-only: callers must use name=value.
  • Parameters before a / are positional-only: callers can't use their names.
def safe_division(numerator, denominator, /, *,
                  ignore_overflow=False, ignore_zero_division=False):
    try:
        return numerator / denominator
    except OverflowError:
        if ignore_overflow:
            return 0
        raise
    except ZeroDivisionError:
        if ignore_zero_division:
            return float("inf")
        raise

print(safe_division(1, 0, ignore_zero_division=True))  # inf
print(safe_division(1.0, 10**500, ignore_overflow=True))  # 0

def safe_division(numerator, denominator, /, *,
                  ignore_overflow=False, ignore_zero_division=False):
    return numerator / denominator

safe_division(1, 0, False, True)
# TypeError: safe_division() takes 2 positional arguments but 4 were given

def safe_division(numerator, denominator, /, *,
                  ignore_overflow=False, ignore_zero_division=False):
    return numerator / denominator

safe_division(numerator=2, denominator=5)
# TypeError: safe_division() got some positional-only arguments passed as keyword arguments: 'numerator, denominator'
Why would you want positional-only parameters? Their names become an implementation detail. You are free to rename numerator to dividend later without breaking anyone's code, because nobody was allowed to call the function using that name. Many built-ins work this way, for example len(obj) and pow(base, exp, mod=None).
Keyword-only parameters, on the other hand, make calls self-documenting and let you add new options later without disturbing the positional ones.
Parameters between / and * can be passed either way: 
def describe(a, b, /, c, *, d):
    return f"a={a} b={b} c={c} d={d}"

print(describe(1, 2, 3, d=4))    # a=1 b=2 c=3 d=4
print(describe(1, 2, c=3, d=4))  # a=1 b=2 c=3 d=4
Combining both markers with *args works naturally too: in def log(message, *values, sep=", ") the parameter sep is keyword-only because it comes after *values.

Type Hints for Functions

Type hints (annotations) describe what types a function expects and returns. Python itself does not enforce them at runtime; they are documentation that tools can check. Editors use them for autocompletion, and static checkers like mypy or pyright use them to catch bugs before you run the code. 
def greet(name: str, times: int = 1) -> str:
    return ", ".join([f"Hello {name}"] * times)

print(greet("Ada", 2))      # Hello Ada, Hello Ada
print(greet.__annotations__)
# {'name': <class 'str'>, 'times': <class 'int'>, 'return': <class 'str'>}

print(greet(42))            # Hello 42  (no runtime error: hints are not enforced)
Modern Python (3.9+) lets you use built-in collection types directly in hints, and 3.10+ adds the | operator for "either type". Here are the most common forms: 
from collections.abc import Callable, Iterable

def total_length(words: list[str]) -> int:
    return sum(len(w) for w in words)

def find_user(users: dict[int, str], user_id: int) -> str | None:
    return users.get(user_id)          # may return None, and the hint says so

def apply(func: Callable[[int], int], values: Iterable[int]) -> list[int]:
    return [func(v) for v in values]

def first[T](items: list[T]) -> T:    # generic function (Python 3.12 syntax)
    return items[0]

print(total_length(["hi", "there"]))   # 7
print(find_user({1: "Ada"}, 2))        # None
print(apply(lambda x: x * x, (1, 2, 3)))  # [1, 4, 9]
print(first(["a", "b"]))               # a
Some practical guidelines:
  • Accept general types (Iterable, Sequence, Mapping) and return specific ones (list, dict). This keeps your function flexible for callers.
  • Annotate *args and **kwargs with the type of each item: *args: int means every positional argument is an int.
  • Use -> None for functions that don't return anything.
def average(*values: float, round_to: int | None = None) -> float:
    result = sum(values) / len(values)
    return round(result, round_to) if round_to is not None else result

print(average(1, 2, 4))              # 2.3333333333333335
print(average(1, 2, 4, round_to=2))  # 2.33
Type hints are not validation. If your function receives data from users or files, you still need to check it explicitly; hints only help you catch mistakes in your own code.

Decorators and functools.wraps

A decorator is a function that takes another function and returns a new function, usually one that runs some extra code before or after the original. It is built on closures. Writing @decorator above a def is just shorthand for func = decorator(func).
Decorators are perfect for cross-cutting concerns that you want to apply to many functions: logging, timing, caching, access checks, retries and so on. 
def trace(func):
    def wrapper(*args, **kwargs):
        result = func(*args, **kwargs)
        print(f"{func.__name__}({args!r}, {kwargs!r}) -> {result!r}")
        return result
    return wrapper

@trace                      # same as: add = trace(add)
def add(a, b):
    """Return the sum of a and b."""
    return a + b

add(2, 3)        # add((2, 3), {}) -> 5
add(2, b=10)     # add((2,), {'b': 10}) -> 12
Notice that wrapper uses *args and **kwargs so it can forward any arguments to the original function.
There is a hidden problem, though: the decorated name now refers to wrapper, not to add. The function's name, docstring and other metadata are lost, which confuses help(), debuggers, and tools like pickle: 
def trace(func):
    def wrapper(*args, **kwargs):
        return func(*args, **kwargs)
    return wrapper

@trace
def add(a, b):
    """Return the sum of a and b."""
    return a + b

print(add.__name__)  # wrapper
print(add.__doc__)   # None
The fix is to decorate the wrapper with functools.wraps. It copies the important metadata (__name__, __doc__, __module__, __qualname__, ...) from the original function to the wrapper, and stores the original in __wrapped__. Always use it when writing decorators. 
from functools import wraps

def trace(func):
    @wraps(func)
    def wrapper(*args, **kwargs):
        return func(*args, **kwargs)
    return wrapper

@trace
def add(a, b):
    """Return the sum of a and b."""
    return a + b

print(add.__name__)              # add
print(add.__doc__)               # Return the sum of a and b.
print(add.__wrapped__(1, 2))     # 3  (call the undecorated original)

Decorators that take arguments

To configure a decorator, add one more layer: a function that receives the options and returns the actual decorator. 
from functools import wraps

def repeat(times):
    def decorator(func):
        @wraps(func)
        def wrapper(*args, **kwargs):
            return [func(*args, **kwargs) for _ in range(times)]
        return wrapper
    return decorator

@repeat(times=3)            # same as: greet = repeat(times=3)(greet)
def greet(name):
    return f"Hi {name}"

print(greet("Ada"))  # ['Hi Ada', 'Hi Ada', 'Hi Ada']
The standard library ships useful ready-made decorators, such as @functools.cache / @functools.lru_cache for memoization, @property, @staticmethod, @classmethod and @dataclasses.dataclass.
from functools import cache

@cache
def fibonacci(n):
    return n if n < 2 else fibonacci(n - 1) + fibonacci(n - 2)

print(fibonacci(80))  # 23416728348467685  (instant, thanks to caching)
