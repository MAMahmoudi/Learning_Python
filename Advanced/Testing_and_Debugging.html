Advanced Testing and Debugging

pytest Fixtures

The Intermediate chapter used setUp() to give every test a fresh object. pytest replaces that idea with fixtures: functions decorated with @pytest.fixture that build something a test needs. A test asks for a fixture simply by naming it as a parameter, and pytest calls the fixture and passes in the result.

Why is this better than setUp()? Each test declares exactly what it needs (nothing more is built), fixtures can depend on other fixtures, they can be shared across many files, and you can control how often they are created. 
# inventory.py
import json


class Inventory:
    def __init__(self):
        self.stock = {}

    def add(self, item, quantity):
        if quantity <= 0:
            raise ValueError("quantity must be positive")
        self.stock[item] = self.stock.get(item, 0) + quantity

    def save(self, path):
        path.write_text(json.dumps(self.stock), encoding="utf-8")

    @classmethod
    def load(cls, path):
        inventory = cls()
        inventory.stock = json.loads(path.read_text(encoding="utf-8"))
        return inventory

# test_inventory.py
import pytest

from inventory import Inventory


@pytest.fixture
def inventory():
    """A fresh Inventory with some stock, rebuilt for every test."""
    inv = Inventory()
    inv.add("apple", 10)
    inv.add("pear", 3)
    return inv


def test_add_existing_item(inventory):
    inventory.add("apple", 5)
    assert inventory.stock["apple"] == 15


def test_each_test_gets_a_fresh_inventory(inventory):
    assert inventory.stock["apple"] == 10      # not 15!


def test_rejects_zero_quantity(inventory):
    with pytest.raises(ValueError):
        inventory.add("kiwi", 0)


def test_save_and_load_round_trip(inventory, tmp_path):
    file = tmp_path / "stock.json"
    inventory.save(file)
    assert file.exists()
    loaded = Inventory.load(file)
    assert loaded.stock == {"apple": 10, "pear": 3}

tmp_path: a built-in fixture

The last test also requests tmp_path, one of pytest's built-in fixtures. It is a pathlib.Path pointing to a brand-new, empty directory that is unique to that test. Tests that write files should always use it instead of writing into the project folder: two tests can never overwrite each other's files, and no junk is left in your working tree. (pytest keeps only the last few runs' temporary directories and removes older ones automatically.) Other useful built-ins include capsys (capture printed output), monkeypatch (temporarily change attributes or environment variables) and caplog (inspect log messages).

Teardown with yield, and fixture scope

If a fixture needs cleaning up, use yield instead of return. Everything before the yield is set-up; the yielded value goes to the test; the code after yield runs once the test has finished, even if it failed.

By default a fixture is created again for every test (scope="function"). For expensive resources you can widen the scope so a single instance is shared:
scope The fixture is created once per...
"function" (default) test
"class" test class
"module" test file
"package" package (folder) of tests
"session" whole pytest run
Fixtures defined in a file named conftest.py are automatically available to every test file in that folder and below, with no import needed. Below, a session-scoped database connection is opened once, and a function-scoped fixture built on top of it empties the table after each test so that tests stay independent: 
# conftest.py
import sqlite3

import pytest


@pytest.fixture(scope="session")
def database():
    print("\n[session] opening database")
    connection = sqlite3.connect(":memory:")
    connection.execute("CREATE TABLE users (name TEXT)")
    yield connection                      # tests run here
    print("\n[session] closing database")
    connection.close()


@pytest.fixture
def clean_users(database):
    yield database
    database.execute("DELETE FROM users")  # undo whatever the test inserted

# test_users.py
def test_insert_user(clean_users):
    clean_users.execute("INSERT INTO users VALUES ('ada')")
    count = clean_users.execute("SELECT COUNT(*) FROM users").fetchone()[0]
    assert count == 1


def test_table_starts_empty(clean_users):
    count = clean_users.execute("SELECT COUNT(*) FROM users").fetchone()[0]
    assert count == 0
Running with -s (do not capture output) shows that the session fixture is set up lazily, the first time a test needs it, and torn down once at the very end:

A wider scope trades isolation for speed. If one test modifies a session-scoped object (adds a row, appends to a list), every later test sees that change, and tests start passing or failing depending on the order they run in. Share only resources that are expensive to create, and reset their state with a function-scoped fixture as shown above. Note also that a fixture can only depend on fixtures of the same or wider scope.
pytest --fixtures lists every available fixture with its docstring, and pytest --fixtures-per-test shows which fixtures each test uses.

Parametrized Tests

Often you want to run the same check against many inputs. Writing a loop inside one test is a poor solution: the first failing input stops the loop, and the report only says that "the test" failed, not which input. @pytest.mark.parametrize instead generates a separate test for each set of arguments, each with its own pass/fail result and its own ID. 
import pytest


def is_palindrome(text):
    cleaned = "".join(ch.lower() for ch in text if ch.isalnum())
    return cleaned == cleaned[::-1]


@pytest.mark.parametrize("text", ["racecar", "Never odd or even", "", "a"])
def test_palindromes(text):
    assert is_palindrome(text)


@pytest.mark.parametrize(
    "text, expected",
    [
        ("level", True),
        ("Level", True),
        ("python", False),
        ("A man, a plan, a canal: Panama", True),
    ],
)
def test_is_palindrome(text, expected):
    assert is_palindrome(text) is expected
The first argument is a string of comma-separated parameter names; the second is a list of values (a tuple per case when there are several names). Use pytest.param when a case needs a readable ID or a mark, for example to record a known failure with xfail ("expected to fail"): 
@pytest.mark.parametrize(
    "a, b, expected",
    [
        pytest.param(2, 3, 5, id="small"),
        pytest.param(-1, 1, 0, id="opposites"),
        pytest.param(0.1, 0.2, 0.3, id="floats",
                     marks=pytest.mark.xfail(reason="float rounding")),
    ],
)
def test_add(a, b, expected):
    assert a + b == expected


# Stacked decorators produce every combination: 2 x 2 = 4 tests.
@pytest.mark.parametrize("x", [1, 2])
@pytest.mark.parametrize("y", ["a", "b"])
def test_combinations(x, y):
    assert len(str(x) + y) == 2

Each case can be run on its own by its ID, e.g. pytest "test_params.py::test_add[small]". If you use unittest, the closest equivalent is self.subTest(): inside a loop, with self.subTest(text=text): reports every failing input separately instead of stopping at the first one.
Parametrize values are evaluated once, when the module is imported. Do not pass mutable objects (a list or dict) that a test modifies; the change would leak into other cases that share the same object. Create such objects inside the test or in a fixture instead.

Mocking with unittest.mock

Real code talks to things that are slow, unreliable or have side effects: web services, databases, the clock, email servers. A unit test should not depend on them. A test that calls a real weather API fails when the network is down and can never test "it is freezing today" on demand. The solution is to replace the collaborator with a mock: a stand-in object that you control and that records how it was used.

The standard library's unittest.mock module provides Mock (and its subclass MagicMock, which also supports magic methods such as __len__). A mock accepts any attribute access and any call; you configure what calls return and then make assertions about how it was called: 
from unittest.mock import Mock

# A Mock accepts any attribute access and any call.
fake_api = Mock()
fake_api.get_price.return_value = 19.99

print(fake_api.get_price("book"))       # 19.99
print(fake_api.get_price.called)        # True
print(fake_api.get_price.call_count)    # 1
print(fake_api.get_price.call_args)     # call('book')

fake_api.get_price.assert_called_once_with("book")   # passes silently

# side_effect as an exception: simulate a failure
fake_api.connect.side_effect = ConnectionError("server down")
try:
    fake_api.connect()
except ConnectionError as error:
    print("Caught:", error)            # Caught: server down

# side_effect as an iterable: a different result on each call
fake_api.next_id.side_effect = [101, 102, 103]
print(fake_api.next_id(), fake_api.next_id())   # 101 102

# side_effect as a function: compute the result from the arguments
fake_api.double.side_effect = lambda n: n * 2
print(fake_api.double(21))              # 42
Attribute / method Purpose
return_value What calling the mock returns
side_effect An exception to raise, an iterable of successive results, or a function to call
assert_called_with(...) The most recent call used these arguments
assert_called_once_with(...) Called exactly once, with these arguments
assert_any_call(...) At least one call used these arguments
assert_not_called() Never called
call_count, call_args, call_args_list Inspect calls manually
When an assertion fails, the message shows what was expected and what actually happened: 
AssertionError: expected call not found.
Expected: save('other')
Actual: save('data')

Replacing real code with patch

Usually the code under test does not receive the collaborator as an argument; it imports it. patch() temporarily replaces a name in a module with a mock and restores the original afterwards. Consider: 
# weather.py
import json
from urllib.request import urlopen


def fetch_temperature(city):
    """Ask a (pretend) web service for the current temperature."""
    with urlopen(f"https://api.example.com/weather?city={city}") as response:
        return json.load(response)["temp_c"]

# advisor.py
from weather import fetch_temperature


def clothing_advice(city):
    try:
        temp = fetch_temperature(city)
    except OSError:
        return "Weather unavailable, bring a jacket just in case."
    if temp < 10:
        return "Wear a coat."
    if temp < 20:
        return "A sweater will do."
    return "T-shirt weather!"
patch works as a decorator (the mock is passed as an extra argument) or as a context manager (the mock is the as target). Keyword arguments such as return_value and side_effect configure the mock directly: 
# test_advisor.py
import unittest
from unittest.mock import patch

from advisor import clothing_advice


class TestClothingAdvice(unittest.TestCase):

    # Patch the name where advisor LOOKS IT UP, not where it was defined.
    @patch("advisor.fetch_temperature")
    def test_cold_day(self, mock_fetch):
        mock_fetch.return_value = 3
        self.assertEqual(clothing_advice("Oslo"), "Wear a coat.")
        mock_fetch.assert_called_once_with("Oslo")

    def test_warm_day(self):
        with patch("advisor.fetch_temperature", return_value=27) as mock_fetch:
            self.assertEqual(clothing_advice("Algiers"), "T-shirt weather!")
        mock_fetch.assert_called_once_with("Algiers")

    @patch("advisor.fetch_temperature", side_effect=OSError("no network"))
    def test_network_failure(self, mock_fetch):
        self.assertIn("unavailable", clothing_advice("Paris"))


if __name__ == "__main__":
    unittest.main()

test_network_failure (test_advisor.TestClothingAdvice.test_network_failure) ... ok
test_warm_day (test_advisor.TestClothingAdvice.test_warm_day) ... ok

OK
Patch where the name is used, not where it is defined. from weather import fetch_temperature copies a reference to the function into the advisor module. Patching "weather.fetch_temperature" replaces the name in weather, but advisor still holds the original, so the real network code runs. In our example the test does not even crash; it silently gets "Weather unavailable, ..." instead of "Wear a coat.". The correct target is "advisor.fetch_temperature". (If advisor had used import weather and called weather.fetch_temperature(), then patching "weather.fetch_temperature" would be correct.)

autospec: mocks that respect the real signature

A plain mock accepts anything. If you rename a function's parameter or change how it is called, tests using a plain mock keep passing while the real code is broken. Creating the mock with autospec=True (or create_autospec()) copies the real object's signature and attributes, so wrong calls fail the test just like they would in production: 
from unittest.mock import create_autospec, patch

from weather import fetch_temperature

loose = patch("advisor.fetch_temperature").start()
print(loose("Oslo", "extra", units="F"))   # <MagicMock name='fetch_temperature()' id='...'>
patch.stopall()                             # the wrong call was accepted without complaint

strict = create_autospec(fetch_temperature, return_value=12)
print(strict("Oslo"))                       # 12
try:
    strict("Oslo", "extra", units="F")
except TypeError as error:
    print("TypeError:", error)              # TypeError: too many positional arguments

with patch("advisor.fetch_temperature", autospec=True) as mock_fetch:
    mock_fetch.return_value = 15
    import advisor
    print(advisor.clothing_advice("Rome"))  # A sweater will do.
Typos are a classic mocking pitfall. mock.sav("data") on a plain mock just creates a new child mock named sav, and an attribute misspelled in your test, such as mock_fetch.retrun_value = 3, silently sets a meaningless attribute instead of configuring the return value. autospec catches the first kind of mistake, because the real object has no sav attribute. (For assertion methods Python helps too: names starting with assert, assret and similar misspellings raise AttributeError instead of passing silently.)
Mock only the boundaries of your system (network, files, time, randomness), not every function. Tests that mock everything mostly check that the code calls what it calls, and they break whenever you refactor.

Encapsulating Dependencies to Make Mocking Easier

patch() is powerful, but needing it is often a sign of hidden dependencies: the function reaches out and grabs something (the clock, a database, a module-level client) instead of being given it. Patching then requires knowing string paths to internal names, and tests break when you move code around.

The alternative is dependency injection: pass collaborators in as parameters (or constructor arguments). Production code passes the real thing, tests pass a fake, and no patching is required. Compare these two versions: 
# Hard to test: depends on the real clock.
from datetime import datetime


def greeting():
    hour = datetime.now().hour          # hidden dependency
    if hour < 12:
        return "Good morning"
    return "Good afternoon"

# Easy to test: the current time can be injected.
from datetime import datetime


def greeting(now=None):
    if now is None:                     # production callers pass nothing
        now = datetime.now()
    if now.hour < 12:
        return "Good morning"
    return "Good afternoon"
Testing the first version in the afternoon can never exercise the morning branch without patching datetime. The second version is tested with plain values: 
from datetime import datetime

from greet import greeting


def test_morning():
    assert greeting(now=datetime(2024, 5, 1, 9, 0)) == "Good morning"


def test_afternoon():
    assert greeting(now=datetime(2024, 5, 1, 15, 30)) == "Good afternoon"
Use None as the default and create the real value inside the function. Writing def greeting(now=datetime.now()) would evaluate datetime.now() once, when the function is defined, so every later call would see the same stale time.

Injecting collaborators into a class

For larger components, pass collaborators to __init__. The class below does not know or care whether it talks to a real database and a real mail server; it only needs objects with the right methods: 
# reminders.py
class ReminderService:
    def __init__(self, repository, sender):
        # Collaborators are handed in instead of being created inside.
        self.repository = repository
        self.sender = sender

    def send_due_reminders(self, today):
        sent = 0
        for user in self.repository.users_with_due_tasks(today):
            self.sender.send(user["email"], f"You have tasks due on {today}")
            sent += 1
        return sent
In tests you can pass Mock objects, or a small hand-written fake that behaves like the real thing in a simplified way. Fakes are often more readable than mocks because you check the resulting state (what ended up in the outbox) rather than a list of calls: 
from datetime import date
from unittest.mock import Mock

from reminders import ReminderService


def test_send_due_reminders():
    repository = Mock()
    repository.users_with_due_tasks.return_value = [
        {"email": "ada@example.com"},
        {"email": "alan@example.com"},
    ]
    sender = Mock()
    service = ReminderService(repository, sender)

    count = service.send_due_reminders(date(2024, 5, 1))

    assert count == 2
    repository.users_with_due_tasks.assert_called_once_with(date(2024, 5, 1))
    sender.send.assert_any_call("ada@example.com", "You have tasks due on 2024-05-01")
    assert sender.send.call_count == 2


class FakeSender:
    """A hand-written test double that records messages instead of emailing."""

    def __init__(self):
        self.outbox = []

    def send(self, address, message):
        self.outbox.append((address, message))


def test_with_a_fake():
    repository = Mock()
    repository.users_with_due_tasks.return_value = [{"email": "ada@example.com"}]
    sender = FakeSender()
    ReminderService(repository, sender).send_due_reminders(date(2024, 5, 1))
    assert sender.outbox == [("ada@example.com", "You have tasks due on 2024-05-01")]
Notice that today is also a parameter rather than being read from the clock inside the method, which is the same idea applied once more. Code designed this way is not only easier to test; it is also easier to reuse (send reminders over SMS by passing a different sender) and to understand, because every dependency is visible in the signature.

Isolating Tests with setUpModule/setUpClass

setUp() runs before every test, which is perfect for cheap objects. Some resources, however, are too expensive to rebuild for each test: starting a database server, loading a large data file, compiling a template set. unittest offers two wider hooks, the counterparts of pytest's module and class fixture scopes:
  • setUpModule() / tearDownModule(): plain functions at module level, run once before the first and after the last test in the file.
  • setUpClass(cls) / tearDownClass(cls): class methods (they need the @classmethod decorator), run once per TestCase class.
The following example prints from every hook so you can see the exact order: 
# test_lifecycle.py
import unittest


def setUpModule():
    print("setUpModule: start the test database server")


def tearDownModule():
    print("tearDownModule: stop the test database server")


class TestUsers(unittest.TestCase):

    @classmethod
    def setUpClass(cls):
        print("  setUpClass: load the large sample dataset once")
        cls.dataset = list(range(1000))

    @classmethod
    def tearDownClass(cls):
        print("  tearDownClass: release the dataset")

    def setUp(self):
        print("    setUp")

    def tearDown(self):
        print("    tearDown")

    def test_dataset_size(self):
        print("      test_dataset_size")
        self.assertEqual(len(self.dataset), 1000)

    def test_dataset_starts_at_zero(self):
        print("      test_dataset_starts_at_zero")
        self.assertEqual(self.dataset[0], 0)


if __name__ == "__main__":
    unittest.main()

(The progress dots are written to stderr and the prints to stdout, so in your terminal they may appear interleaved differently.)

The golden rule: share expensive, read-only resources; isolate everything a test changes. Put the costly part in setUpClass and give each test its own mutable state in setUp. The cleanup helpers addClassCleanup() and addCleanup() register undo actions right next to the code that creates the resource; they run in reverse order even if a later part of the set-up raises an exception, something a tearDown method cannot guarantee: 
import shutil
import tempfile
import unittest
from pathlib import Path


class TestReports(unittest.TestCase):

    @classmethod
    def setUpClass(cls):
        cls.folder = Path(tempfile.mkdtemp())
        # Registered cleanups run even if a later line in setUpClass fails.
        cls.addClassCleanup(shutil.rmtree, cls.folder)
        (cls.folder / "template.txt").write_text("Hello {name}")

    def setUp(self):
        # Each test gets its own output file, so tests cannot interfere.
        self.output = self.folder / f"{self.id()}.txt"
        self.addCleanup(self.output.unlink, missing_ok=True)

    def test_render(self):
        template = (self.folder / "template.txt").read_text()
        self.output.write_text(template.format(name="Ada"))
        self.assertEqual(self.output.read_text(), "Hello Ada")


if __name__ == "__main__":
    unittest.main()
If setUpClass raises an exception, none of the tests in the class run and tearDownClass is not called, so any resource opened before the error leaks. That is exactly why addClassCleanup() exists. The same applies to setUpModule with unittest.addModuleCleanup().
Attributes stored on cls in setUpClass are shared by every test in the class. If one test appends to self.dataset, the next test sees the modified list. Treat class-level data as read-only.

Test Coverage

How do you know whether your tests exercise all of your code? Coverage tools record which lines run while the test suite executes and report the ones that never did. Those unexecuted lines are code that no test has ever checked. The standard tool is coverage.py: 
> python -m pip install coverage
Take this function, which has several branches, and a test file that checks only two of them: 
# shipping.py
def shipping_cost(weight_kg, express=False):
    if weight_kg <= 0:
        raise ValueError("weight must be positive")
    if weight_kg < 1:
        cost = 4.0
    elif weight_kg < 5:
        cost = 9.5
    else:
        cost = 9.5 + (weight_kg - 5) * 1.2
    if express:
        cost *= 2
    return round(cost, 2)

# test_shipping.py
from shipping import shipping_cost


def test_light_parcel():
    assert shipping_cost(0.5) == 4.0


def test_medium_parcel():
    assert shipping_cost(3) == 9.5
Instead of python -m pytest (or python -m unittest), run the tests through coverage run -m, then ask for a report. The -m option of report adds the "Missing" column listing the line numbers that never ran: 
> coverage run -m pytest
2 passed in 0.02s
> coverage report -m
Name               Stmts   Miss  Cover   Missing
------------------------------------------------
shipping.py           11      3    73%   3, 9, 11
test_shipping.py       5      0   100%
------------------------------------------------
TOTAL                 16      3    81%
Lines 3, 9 and 11 are the error case, the heavy-parcel formula and the express surcharge: exactly the behaviors we forgot to test. coverage html writes an htmlcov/index.html report in which every file is shown with the missed lines highlighted, which is the most convenient way to explore the results.

Branch coverage

Line coverage can be misleading. In the function below a single test executes every line, yet the case where the if is false was never tried: 
# pricing.py
def final_price(price, coupon=None):
    if coupon == "SAVE5":
        price -= 5
    return max(price, 0)


# test_pricing.py
from pricing import final_price


def test_coupon_applied():
    assert final_price(20, "SAVE5") == 15
Adding --branch makes coverage track every possible jump. 2->4 means "the jump from line 2 straight to line 4 (the condition being false) never happened": 
> coverage run -m pytest
> coverage report -m --include=pricing.py
Name         Stmts   Miss  Cover   Missing
------------------------------------------
pricing.py       4      0   100%
------------------------------------------
TOTAL            4      0   100%

> coverage run --branch -m pytest
> coverage report -m --include=pricing.py
Name         Stmts   Miss Branch BrPart  Cover   Missing
--------------------------------------------------------
pricing.py       4      0      2      1    83%   2->4
--------------------------------------------------------
TOTAL            4      0      2      1    83%
Settings can be stored in a .coveragerc file (or in pyproject.toml under [tool.coverage.run] and [tool.coverage.report]) so you do not have to repeat them. With fail_under, coverage report exits with an error status when coverage drops below the threshold, which lets a CI pipeline reject changes that remove tests: 
# .coveragerc
[run]
branch = True
omit = test_*.py

[report]
show_missing = True
fail_under = 90

> coverage run -m pytest
> coverage report
Name         Stmts   Miss Branch BrPart  Cover   Missing
--------------------------------------------------------
pricing.py       4      0      2      1    83%   2->4
--------------------------------------------------------
TOTAL            4      0      2      1    83%
Coverage failure: total of 83 is less than fail-under=90
100% coverage does not mean the code is correct. Coverage only proves a line was executed, not that any assertion checked its result: a test that calls every function and asserts nothing scores 100%. Use coverage to find untested code, not as a goal in itself.
If you use pytest, the pytest-cov plugin wraps the same engine: pytest --cov=shipping --cov-report=term-missing.

Post-Mortem Debugging

Placing a breakpoint() requires knowing in advance where to stop. When a program crashes with an exception you did not expect, it is often more useful to do post-mortem debugging: open the debugger at the moment of the crash, with every local variable of every frame still available for inspection. Instead of reading a traceback and guessing, you can look at the exact data that caused the failure. 
# invoice.py
def unit_price(line):
    return line["total"] / line["quantity"]


def summarize(lines):
    return [round(unit_price(line), 2) for line in lines]


orders = [
    {"product": "pen", "total": 6.0, "quantity": 3},
    {"product": "gift card", "total": 25.0, "quantity": 0},
]
print(summarize(orders))

python -m pdb script.py

Running a script under python -m pdb starts it paused on the first line. Type c to run it normally; if it raises an uncaught exception, pdb automatically enters post-mortem mode at the line that failed. Use u (up) to move to the calling frame and inspect its variables: 
> python -m pdb invoice.py

pdb.pm() in the interactive interpreter

If you ran the script with python -i invoice.py (which drops into the interactive prompt after the program ends or crashes), or you hit an exception while experimenting in the REPL, call pdb.pm(). It opens the debugger on the last unhandled exception, which Python stores in sys.last_exc (new in 3.12; older versions use sys.last_traceback): 
> python -i invoice.py
Traceback (most recent call last):
  ...
ZeroDivisionError: float division by zero
>>> import pdb
>>> pdb.pm()
> invoice.py(2)unit_price()
-> return line["total"] / line["quantity"]
(Pdb) p line["product"]
'gift card'

pdb.post_mortem() inside your code

To debug an exception that your program catches, call pdb.post_mortem() inside the except block. Without arguments it uses the exception currently being handled: 
import pdb


def risky(data):
    return data["missing"]


try:
    risky({"present": 1})
except Exception:
    print("Something went wrong, opening the debugger...")
    pdb.post_mortem()            # uses the exception currently being handled

Something went wrong, opening the debugger...
> pm_except.py(5)risky()
-> return data["missing"]
(Pdb) p data
{'present': 1}
pytest has the same feature built in: pytest --pdb opens the debugger at the point of every failing test (combine it with -x to stop after the first one), and pytest --trace stops at the start of each test.
Never leave pdb.post_mortem() in code that runs unattended (a server, a scheduled job): the process will hang forever waiting for keyboard input. Log the exception with logger.exception() instead.

Finding Memory Leaks with tracemalloc

Python frees memory automatically once nothing refers to an object anymore. A "memory leak" in Python therefore almost always means that something still holds a reference to objects you no longer need: a cache that only grows, a list of callbacks that is never cleared, a global collection of results. The program's memory use creeps up until it slows down or crashes.

The standard tracemalloc module records the source line responsible for each memory allocation. The usual technique is to take a snapshot before and after the suspicious work and compare them; the lines whose memory grew the most are your suspects: 
import tracemalloc

_cache = []                       # module-level list that is never cleared


def process_request(request_id):
    payload = "x" * 10_000        # about 10 KB of data per request
    _cache.append(payload)        # BUG: every payload is kept forever
    return len(payload)


tracemalloc.start()
before = tracemalloc.take_snapshot()

for request_id in range(1_000):
    process_request(request_id)

after = tracemalloc.take_snapshot()
top_stats = after.compare_to(before, "lineno")

print("Top 3 memory differences:")
for stat in top_stats[:3]:
    print(stat)

current, peak = tracemalloc.get_traced_memory()
print(f"Current: {current / 1024:.0f} KiB, peak: {peak / 1024:.0f} KiB")
tracemalloc.stop()

Top 3 memory differences:
leak.py:7: size=9806 KiB (+9806 KiB), count=1000 (+1000), average=10041 B
leak.py:8: size=8800 B (+8800 B), count=1 (+1), average=8800 B
C:\Python312\Lib\tracemalloc.py:560: size=312 B (+312 B), count=2 (+2), average=156 B
The report is unambiguous: line 7 allocated about 9.8 MB in 1000 blocks that are still alive after the loop. The strings were created there, but they survive because line 8 stores them in _cache. Fixing the leak means removing that reference, bounding the cache (for example with functools.lru_cache(maxsize=...) or a collections.deque with maxlen), or clearing it periodically.

Seeing the full call path

Knowing the line that allocated memory is not always enough: a helper such as load_row() may be called from many places, and you need to know which caller keeps the results alive. Pass a number of frames to tracemalloc.start() and group statistics by "traceback": 
import tracemalloc

tracemalloc.start(10)              # remember up to 10 frames per allocation

_cache = []


def load_row(i):
    return {"id": i, "data": str(i) * 1_000}


def remember(i):
    _cache.append(load_row(i))


for i in range(500):
    remember(i)

snapshot = tracemalloc.take_snapshot()
biggest = snapshot.statistics("traceback")[0]
print(f"{biggest.count} blocks, {biggest.size / 1024:.1f} KiB")
for line in biggest.traceback.format():
    print(line)

1473 blocks, 1464.6 KiB
  File "leak_tb.py", line 17
    remember(i)
  File "leak_tb.py", line 13
    _cache.append(load_row(i))
  File "leak_tb.py", line 9
    return {"id": i, "data": str(i) * 1_000}
Tracing every allocation makes the program noticeably slower and uses extra memory itself, and storing more frames costs more. Enable tracemalloc while investigating, not permanently in production. Also, it only sees memory allocated through Python's allocator; memory used internally by C extensions may not appear.
You can also enable tracing for a whole program without editing it: python -X tracemalloc=10 app.py (or set the PYTHONTRACEMALLOC environment variable). A related trick: gc.get_referrers(obj) lists the objects that refer to obj, which helps when you know what is leaking but not who is holding it.

Doctest

Examples in documentation are wonderfully helpful and notoriously prone to going stale: the code changes and nobody updates the docstring. The standard doctest module solves this by treating examples written like an interactive session, lines starting with >>> followed by the expected output, as tests. It runs each example and compares the printed result with what the docstring claims. 
# stats.py
def mean(values):
    """Return the arithmetic mean of a non-empty list of numbers.

    >>> mean([1, 2, 3, 4])
    2.5
    >>> mean([10])
    10.0
    >>> mean([])
    Traceback (most recent call last):
        ...
    ValueError: mean() requires at least one value
    """
    if not values:
        raise ValueError("mean() requires at least one value")
    return sum(values) / len(values)


def describe(values):
    """Summarize a list of numbers.

    >>> summary = describe([3, 1, 2])
    >>> summary["min"], summary["max"]
    (1, 3)
    >>> sorted(summary)
    ['max', 'mean', 'min']
    >>> describe(list(range(100)))  # doctest: +ELLIPSIS
    {'min': 0, 'max': 99, 'mean': 49.5...}
    """
    return {"min": min(values), "max": max(values), "mean": mean(values)}


if __name__ == "__main__":
    import doctest
    doctest.testmod()
A few rules to notice: the expected output is exactly what the REPL would display (the repr() of the value), an expected exception needs only the Traceback header and the final line (the middle can be ...), and the +ELLIPSIS directive lets ... in the expected output match any text. There are several ways to run the examples. Doctest is silent when everything passes, so add -v to see details: 
> python stats.py                 # runs doctest.testmod(); no output means success
> python -m doctest stats.py      # no need for the __main__ block
> python -m doctest -v stats.py
...
1 items had no tests:
    stats
2 items passed all tests:
   4 tests in stats.describe
   3 tests in stats.mean
7 tests in 3 items.
7 passed and 0 failed.
Test passed.

> pytest --doctest-modules stats.py
2 passed in 0.06s
When an example is wrong, doctest shows what it expected and what it actually got: 
**********************************************************************
File "stats_bad.py", line 5, in stats_bad.mean
Failed example:
    mean([1, 2, 3, 4])
Expected:
    2
Got:
    2.5
**********************************************************************
1 items had failures:
   1 of   2 in stats_bad.mean
***Test Failed*** 1 failures.
Doctest compares text, not values. Output that varies between runs breaks it: memory addresses (<object at 0x...>), timestamps, set ordering, and long float results such as 0.30000000000000004. Make such examples deterministic, for example by printing sorted(...), rounding numbers, or using +ELLIPSIS. Trailing whitespace in the expected output also causes confusing failures.
Doctests are best for keeping documentation honest and showing typical usage. They are a poor fit for thorough testing with many edge cases, set-up, or mocks; keep those in your unittest or pytest suite and let the two complement each other.
