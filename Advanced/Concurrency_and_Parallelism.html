Concurrency and Parallelism

Concurrency vs Parallelism

These two words are often used as if they meant the same thing, but they describe different ideas:
  • Concurrency means a program is dealing with many tasks at once. The tasks take turns making progress, so they appear to run at the same time, even on a single CPU core. A chef who puts water on to boil, then chops vegetables while waiting, is working concurrently.
  • Parallelism means a program is doing many tasks at literally the same instant, on several CPU cores. Two chefs chopping vegetables side by side are working in parallel.
The key question to ask about any slow program is what is it waiting for?
  • If it spends most of its time waiting on the outside world (network requests, disk reads, databases, sleeping, user input) it is I/O-bound. Concurrency helps: while one task waits, another can run.
  • If it spends most of its time calculating (number crunching, image processing, compression) it is CPU-bound. Only true parallelism (more cores working) makes it faster.

The Global Interpreter Lock (GIL)

The standard Python interpreter (CPython) has a Global Interpreter Lock: a single lock that a thread must hold to execute Python bytecode. It exists because CPython's memory management (reference counting) is not thread-safe on its own, and a single lock is a simple and fast way to protect it.
The consequence is important:
  • Several threads in one process cannot run Python code in parallel. Only one thread executes Python bytecode at any given moment.
  • A thread releases the GIL while it waits for I/O (and while some C extensions such as NumPy or hashlib do heavy work). That is why threads still speed up I/O-bound programs.
  • To use several cores for pure-Python CPU work, you need several processes, each with its own interpreter and its own GIL.
You can see the effect yourself: running a CPU-heavy function in two threads takes about as long as running it twice in a row. 
import threading
import time

def count_down(n):
    while n > 0:
        n -= 1

N = 5_000_000

start = time.perf_counter()
count_down(N)
count_down(N)
print(f"Sequential: {time.perf_counter() - start:.2f}s")

start = time.perf_counter()
t1 = threading.Thread(target=count_down, args=(N,))
t2 = threading.Thread(target=count_down, args=(N,))
t1.start(); t2.start()
t1.join(); t2.join()
print(f"Two threads: {time.perf_counter() - start:.2f}s")

# Typical output (numbers vary by machine):
# Sequential: 0.40s
# Two threads: 0.41s   <- no speed-up because of the GIL
Python 3.13 introduced an optional free-threaded build (PEP 703, often called "no-GIL" and installed as python3.13t) in which threads can truly run in parallel. It is still experimental: many third-party packages are not yet compatible, and single-threaded code may run somewhat slower. For everyday work, assume the GIL is present. You can check with sys._is_gil_enabled() on 3.13+.

Managing Child Processes with subprocess

The simplest form of parallelism is to launch another program. The subprocess module starts child processes, lets you pass them input, and collects their output and exit code. Child processes run truly in parallel with your Python program because they are completely separate operating-system processes, unaffected by the GIL.
For most cases, use subprocess.run(). It starts the command, waits for it to finish and returns a CompletedProcess object. 
import subprocess
import sys

# sys.executable is the path of the Python interpreter running this script,
# so this example works on Windows, macOS and Linux alike.
result = subprocess.run(
    [sys.executable, "-c", "print('Hello from a child process')"],
    capture_output=True,   # collect stdout and stderr
    text=True,             # decode bytes to str
    check=True,            # raise CalledProcessError if the exit code is not 0
)
print(result.returncode)        # 0
print(result.stdout.strip())    # Hello from a child process
Pass the command as a list of arguments rather than a single string. Each argument is then delivered to the program exactly as written, so file names containing spaces or special characters cannot be misinterpreted.
Avoid shell=True with any text that comes from users. The shell would interpret characters such as ;, & or |, which allows command injection. Also, without check=True a failing command is silently ignored unless you inspect returncode yourself.

Running children in parallel with Popen

subprocess.Popen starts a process and returns immediately, so you can start several children, let them run side by side, and then wait for all of them. Use communicate() to send input and read output; it also accepts a timeout so a stuck child cannot hang your program forever. 
import subprocess
import sys
import time

code = "import time; time.sleep(0.5); print('done')"

start = time.perf_counter()
procs = [subprocess.Popen([sys.executable, "-c", code], stdout=subprocess.PIPE, text=True)
         for _ in range(4)]

for proc in procs:
    try:
        out, _ = proc.communicate(timeout=10)
    except subprocess.TimeoutExpired:
        proc.kill()          # never leave a runaway child behind
        out, _ = proc.communicate()
    print(out.strip())

elapsed = time.perf_counter() - start
print(f"4 children took {elapsed:.1f}s")   # about 0.5-1s, not 2s: they ran in parallel

Threads for Blocking I/O

A thread is an independent flow of execution inside the same process. All threads share the same memory, so they can easily read the same variables. Because the GIL is released while a thread waits on I/O, threads are a good fit when your program spends its time blocked: downloading files, calling web APIs, querying databases or talking to hardware.
The threading.Thread class takes a target function and its args. Call start() to launch it and join() to wait until it finishes. 
import threading
import time

def fake_download(name):
    time.sleep(0.3)  # stands in for a slow network call; the GIL is released here
    print(f"{name} finished")

start = time.perf_counter()
threads = []
for i in range(5):
    t = threading.Thread(target=fake_download, args=(f"file{i}",))
    t.start()
    threads.append(t)

for t in threads:
    t.join()   # wait for every thread before continuing

print(f"Total: {time.perf_counter() - start:.1f}s")  # about 0.3s instead of 1.5s
The five "downloads" overlap, so the total time is close to that of a single one. The order in which the threads print is not guaranteed; the operating system decides when each thread runs.
  • Forgetting join() means your main code may continue (and read results) before the threads are done.
  • An exception raised inside a thread does not propagate to the code that started it; it is only printed. Collect results and errors explicitly, or use concurrent.futures (below), which does this for you.
  • Threads are not free: each one reserves memory for its stack. Starting thousands of threads is wasteful; use a thread pool or asyncio instead.
A thread created with daemon=True is killed abruptly when the main program exits. That is handy for background helpers, but never use daemon threads for work that must finish cleanly, such as writing a file.

Preventing Data Races with Lock

A common misconception is that the GIL makes your code thread-safe. It does not. The GIL protects the interpreter's internals, but the interpreter can switch threads between any two bytecode instructions. An innocent-looking statement such as counter += 1 is really three steps: read the value, add one, store the result. If two threads interleave those steps, one of the updates is lost. This is called a data race.
In real programs a race may strike only once in millions of runs, which is exactly what makes it so hard to find. In the demonstration below, time.sleep(0) asks the interpreter to switch threads between the read and the write, so the bug shows up every time. 
import threading
import time

class Counter:
    def __init__(self):
        self.count = 0

    def increment(self):
        value = self.count      # 1. read
        time.sleep(0)           #    let another thread run here (widens the race window)
        self.count = value + 1  # 2. modify and write, possibly using a stale value!

def worker(counter, times):
    for _ in range(times):
        counter.increment()

counter = Counter()
threads = [threading.Thread(target=worker, args=(counter, 10_000)) for _ in range(5)]
for t in threads: t.start()
for t in threads: t.join()
print(counter.count)  # Expected 50000, but far less, e.g. 10127 (varies run to run)
The fix is a threading.Lock (a mutex, short for mutual exclusion). Only one thread at a time can hold the lock; others that try to acquire it wait until it is released. Use it as a context manager with with, so the lock is always released, even if an exception occurs. 
import threading
import time

class SafeCounter:
    def __init__(self):
        self.count = 0
        self.lock = threading.Lock()

    def increment(self):
        with self.lock:            # acquire ... release automatically
            value = self.count
            time.sleep(0)          # other threads may run, but cannot enter this block
            self.count = value + 1

def worker(counter, times):
    for _ in range(times):
        counter.increment()

counter = SafeCounter()
threads = [threading.Thread(target=worker, args=(counter, 10_000)) for _ in range(5)]
for t in threads: t.start()
for t in threads: t.join()
print(counter.count)  # 50000, every time
Things to Remember
  • Protect every piece of shared, mutable state that more than one thread writes to.
  • Keep the code inside with lock: short. Holding a lock while doing slow I/O makes the other threads wait and destroys the benefit of threading.
  • If a function holding a lock calls another function that tries to take the same Lock, the thread blocks forever (a deadlock). Use threading.RLock (re-entrant lock) when the same thread may acquire it again.
  • When several locks are needed, always acquire them in the same order in every thread to avoid deadlocks.

Coordinating Work with Queue

Many concurrent programs form a pipeline: one stage produces items (for example, URLs to download), another stage consumes them. Passing data between threads through a shared list plus your own locks is error-prone. The queue.Queue class is a thread-safe FIFO queue that already does all the locking for you:
  • put(item) adds an item. With maxsize set, it blocks when the queue is full, which stops a fast producer from using unlimited memory (this is called back-pressure).
  • get() removes an item and blocks while the queue is empty, so consumers don't need to busy-wait.
  • task_done() and join() let you wait until every item has been processed.
A common way to tell consumers to stop is to send a special sentinel value (often None), one per consumer. 
import queue
import threading
import time

SENTINEL = None
work = queue.Queue(maxsize=3)     # bounded: producer waits if consumers fall behind
results = queue.Queue()

def producer(n_items, n_consumers):
    for i in range(n_items):
        work.put(i)               # blocks while the queue is full
    for _ in range(n_consumers):
        work.put(SENTINEL)        # one "stop" signal per consumer

def consumer():
    while True:
        item = work.get()         # blocks while the queue is empty
        if item is SENTINEL:
            break
        time.sleep(0.05)          # simulate slow work
        results.put(item * item)

N_CONSUMERS = 3
consumers = [threading.Thread(target=consumer) for _ in range(N_CONSUMERS)]
for c in consumers: c.start()
producer(10, N_CONSUMERS)
for c in consumers: c.join()

squares = sorted(results.get() for _ in range(results.qsize()))
print(squares)  # [0, 1, 4, 9, 16, 25, 36, 49, 64, 81]
queue.Queue is for threads. Use asyncio.Queue inside coroutines and multiprocessing.Queue between processes. For a simple single-threaded queue, collections.deque is faster.

ThreadPoolExecutor and concurrent.futures

Creating threads by hand, collecting their results and handling their errors takes a lot of boilerplate. The concurrent.futures module provides a higher-level interface: an executor owns a fixed pool of worker threads and reuses them for many tasks.
executor.submit(fn, *args) schedules a call and immediately returns a Future, an object representing a result that will be available later. Calling future.result() waits for the value, and, unlike raw threads, re-raises any exception that happened in the worker. 
from concurrent.futures import ThreadPoolExecutor, as_completed
import time

def fetch(url):
    time.sleep(0.2)                  # pretend this is a network request
    if "bad" in url:
        raise ValueError(f"cannot fetch {url}")
    return f"<html of {url}>"

urls = ["a.com", "b.com", "bad.com", "c.com"]

with ThreadPoolExecutor(max_workers=4) as executor:      # pool shuts down at the end of with
    futures = {executor.submit(fetch, url): url for url in urls}
    for future in as_completed(futures):                # yields futures as they finish
        url = futures[future]
        try:
            print(url, "->", future.result())
        except ValueError as exc:
            print(url, "failed:", exc)

# Output order varies, e.g.:
# b.com -> <html of b.com>
# bad.com failed: cannot fetch bad.com
# a.com -> <html of a.com>
# c.com -> <html of c.com>
When you simply want to apply one function to many inputs and keep the original order, use executor.map(). It works like the built-in map but runs the calls concurrently. 
from concurrent.futures import ThreadPoolExecutor
import time

def slow_square(x):
    time.sleep(0.1)
    return x * x

start = time.perf_counter()
with ThreadPoolExecutor(max_workers=5) as executor:
    results = list(executor.map(slow_square, range(10)))
print(results)  # [0, 1, 4, 9, 16, 25, 36, 49, 64, 81]  (always in input order)
print(f"{time.perf_counter() - start:.1f}s")  # about 0.2s instead of 1.0s
With executor.map(), an exception from any call is raised when you reach that result while iterating, and the remaining results are lost. Use submit() with as_completed() when you need to handle failures one by one.

Coroutines with async/await and asyncio

Threads are scheduled by the operating system, which can interrupt them at any point. That is exactly why they need locks. Coroutines take a different approach: they are functions that voluntarily pause at every await, handing control back to an event loop, which then runs another coroutine that is ready. All of this happens in a single thread.
Advantages over threads:
  • Very cheap: you can have tens of thousands of coroutines (for example, one per network connection), where the same number of threads would exhaust memory.
  • Switches only happen at await, so the code between two awaits runs without interruption, which makes many races impossible.
The vocabulary:
  • async def defines a coroutine function. Calling it does not run it; it returns a coroutine object.
  • await runs a coroutine (or other awaitable) and pauses the current one until the result is ready.
  • asyncio.run(main()) creates the event loop, runs main to completion and closes the loop. It is the usual entry point of an async program.
import asyncio

async def greet(name, delay):
    await asyncio.sleep(delay)   # non-blocking sleep: lets other coroutines run
    print(f"Hello, {name}")
    return name.upper()

async def main():
    result = await greet("Ada", 0.1)   # awaiting one coroutine runs it to completion
    print(result)

asyncio.run(main())
# Hello, Ada
# ADA

Running coroutines concurrently: gather and create_task

Awaiting coroutines one after another runs them sequentially. To run them concurrently, wrap them in tasks. asyncio.gather() runs several awaitables at once and returns their results in the same order you passed them. asyncio.create_task() schedules a single coroutine to start running in the background, so you can do other things before awaiting it. 
import asyncio
import time

async def fetch(name, delay):
    await asyncio.sleep(delay)
    return f"{name} ({delay}s)"

async def main():
    start = time.perf_counter()

    # gather: results come back in argument order
    results = await asyncio.gather(fetch("a", 0.3), fetch("b", 0.1), fetch("c", 0.2))
    print(results)  # ['a (0.3s)', 'b (0.1s)', 'c (0.2s)']

    # create_task: start now, await later
    task = asyncio.create_task(fetch("background", 0.2))
    print("doing other work while the task runs...")
    print(await task)  # background (0.2s)

    print(f"elapsed {time.perf_counter() - start:.1f}s")  # about 0.5s, not 0.8s

asyncio.run(main())

Structured concurrency with TaskGroup (Python 3.11+)

asyncio.TaskGroup is the modern, safer way to run a group of tasks. The async with block does not exit until every task in the group has finished. If one task fails, the group cancels the others and raises the errors together as an ExceptionGroup, which you catch with except*. With plain gather(), the remaining tasks keep running after a failure, which can leak work. 
import asyncio

async def job(n):
    await asyncio.sleep(0.1 * n)
    if n == 2:
        raise ValueError("job 2 failed")
    return n * 10

async def main():
    async with asyncio.TaskGroup() as tg:
        t1 = tg.create_task(job(1))
        t3 = tg.create_task(job(3))
    print(t1.result(), t3.result())  # 10 30

    try:
        async with asyncio.TaskGroup() as tg:
            tg.create_task(job(1))
            tg.create_task(job(2))
            tg.create_task(job(5))   # cancelled when job 2 fails
    except* ValueError as group:
        for exc in group.exceptions:
            print("caught:", exc)    # caught: job 2 failed

asyncio.run(main())
  • Never call blocking functions inside a coroutine. time.sleep(), requests.get() or a long CPU loop freeze the entire event loop, and every other coroutine stops with it. Use async libraries (asyncio.sleep, aiohttp, httpx) or move the blocking call to a thread (next section).
  • Forgetting await is a classic bug: the coroutine never runs and Python warns RuntimeWarning: coroutine '...' was never awaited.
  • Keep a reference to tasks made with create_task() (or use a TaskGroup); the event loop only keeps a weak reference, so an unreferenced task can be garbage-collected before it finishes.

Mixing Threads and Coroutines

Real programs rarely start fresh. You may want to use asyncio, but depend on a library that only offers blocking functions (a database driver, a file API, an older HTTP client). Calling it directly would block the event loop. asyncio.to_thread(func, *args) (Python 3.9+) runs the blocking function in a background thread and gives you an awaitable, so the event loop keeps serving other coroutines in the meantime. 
import asyncio
import time

def blocking_read(name):
    time.sleep(0.3)          # a legacy, blocking call we cannot change
    return f"data from {name}"

async def heartbeat():
    for _ in range(3):
        print("event loop is still responsive")
        await asyncio.sleep(0.1)

async def main():
    start = time.perf_counter()
    results = await asyncio.gather(
        asyncio.to_thread(blocking_read, "disk"),
        asyncio.to_thread(blocking_read, "legacy-db"),
        heartbeat(),
    )
    print(results[:2])  # ['data from disk', 'data from legacy-db']
    print(f"{time.perf_counter() - start:.1f}s")  # about 0.3s

asyncio.run(main())
The opposite direction also comes up: ordinary (synchronous) code in another thread needs to run a coroutine on an event loop that is already running. Use asyncio.run_coroutine_threadsafe(coro, loop), which returns a concurrent.futures.Future you can wait on from that thread.
A good migration strategy for a large program is top-down or bottom-up, one layer at a time: convert a function to async def, and use to_thread at the boundary for the parts you have not converted yet.
to_thread is meant for I/O-bound blocking calls. Because of the GIL, putting CPU-heavy code in a thread will not make it faster; use loop.run_in_executor() with a ProcessPoolExecutor for that.

True Parallelism with ProcessPoolExecutor and multiprocessing

For CPU-bound pure-Python work, the way around the GIL is to use several processes. Each worker process has its own interpreter, its own memory and its own GIL, so they can keep every CPU core busy.
ProcessPoolExecutor has exactly the same interface as ThreadPoolExecutor, so switching between them is often a one-word change. 
from concurrent.futures import ProcessPoolExecutor
import time

def count_primes(limit):
    """Deliberately slow, CPU-bound work."""
    count = 0
    for n in range(2, limit):
        if all(n % d for d in range(2, int(n ** 0.5) + 1)):
            count += 1
    return count

if __name__ == "__main__":          # REQUIRED on Windows and macOS (see below)
    limits = [60_000] * 4

    start = time.perf_counter()
    serial = [count_primes(x) for x in limits]
    print(f"serial:   {time.perf_counter() - start:.2f}s")

    start = time.perf_counter()
    with ProcessPoolExecutor() as executor:     # defaults to one worker per CPU core
        parallel = list(executor.map(count_primes, limits))
    print(f"parallel: {time.perf_counter() - start:.2f}s")

    print(serial == parallel, parallel[0])  # True 6057
# Typical output on a 4+ core machine:
# serial:   0.60s
# parallel: 0.25s

Why the if __name__ == "__main__": guard is required

On Windows (and on macOS by default) new processes are created with the spawn method: each worker starts a fresh Python interpreter and imports your main module to find the function it must run. Without the guard, that import would execute your top-level code again, which would create another pool, which would spawn more workers... Python detects this and raises a RuntimeError. With the guard, the setup code only runs in the parent process.
For the same reason, the function you send to a worker must be defined at the top level of a module (lambdas and nested functions cannot be pickled), and it will not work from an interactive prompt or some notebooks.

The multiprocessing module

concurrent.futures is built on top of multiprocessing, which also offers lower-level tools: Process (like Thread), Pool, Queue and shared-memory objects. 
import multiprocessing as mp

def square(x):
    return x * x

def report(q, name):
    q.put(f"hello from {name} (pid {mp.current_process().pid})")

if __name__ == "__main__":
    with mp.Pool(processes=4) as pool:
        print(pool.map(square, range(8)))   # [0, 1, 4, 9, 16, 25, 36, 49]

    q = mp.Queue()
    p = mp.Process(target=report, args=(q, "worker-1"))
    p.start()
    print(q.get())   # hello from worker-1 (pid 12345)
    p.join()
Processes do not share memory. Arguments and return values are pickled and copied between processes, which has a real cost. Parallelism pays off when each task does a lot of computation compared to the data it sends and receives. Sending a huge list to compute a tiny result can make the "parallel" version slower than the serial one.

Choosing the Right Tool

Start by measuring where your program spends its time, then pick the simplest tool that fits:
Tool Best for Runs in parallel? Main pitfalls
subprocess Running external programs and command-line tools Yes (separate processes) Shell injection, forgetting timeouts and exit codes
threading / ThreadPoolExecutor A moderate number of blocking I/O tasks; using blocking libraries No for Python code (GIL); yes while waiting on I/O Data races, need for locks, memory cost per thread
asyncio Thousands of concurrent network connections; high-concurrency I/O No (one thread, cooperative switching) Any blocking call freezes everything; needs async-aware libraries
asyncio.to_thread Calling blocking code from async code Only during I/O waits No help for CPU-bound work
ProcessPoolExecutor / multiprocessing CPU-bound pure-Python work Yes (one interpreter per core) Pickling overhead, __main__ guard, no shared memory

Things to Remember
  • I/O-bound: threads or asyncio. CPU-bound: processes (or a C extension such as NumPy that releases the GIL).
  • Prefer the high-level tools (concurrent.futures, TaskGroup, Queue) over manual threads and locks.
  • Concurrency adds complexity. If the program is fast enough sequentially, keep it sequential.
