Collaboration

Know Where to Find Community-Built Modules

Python's standard library is large ("batteries included"), but the real strength of the language is its community. The Python Package Index (PyPI, at pypi.org) hosts hundreds of thousands of open-source packages: requests and httpx for HTTP, numpy and pandas for data, pytest for testing, django and fastapi for the web, and many more. Before writing something complicated yourself, check whether a well-maintained package already solves it.
Packages are installed with pip, the package installer that ships with Python. Running it as python -m pip guarantees that the packages go to the same interpreter you will run your code with, which avoids the classic "I installed it but Python can't find it" problem. 
python -m pip install requests            # latest version
python -m pip install "requests==2.32.3"  # an exact version
python -m pip install --upgrade requests  # upgrade to the newest version
python -m pip show requests               # version, location, dependencies
python -m pip list                        # everything installed
python -m pip uninstall requests
How to choose between packages that do similar things:
  • Is it maintained? Look at the date of the latest release and recent activity in its repository.
  • Is it popular and documented? Widely used packages have fewer surprises and more answers online.
  • Does its license allow your use (MIT, BSD and Apache are permissive; GPL has stronger conditions)?
  • How many dependencies does it pull in? Each one is code you now rely on.
Anyone can upload to PyPI. Attackers publish typosquatting packages whose names are one letter away from popular ones (for example reqeusts) and contain malware. Double-check the spelling and the project page before installing, and never run pip with administrator rights to install into the system Python.

Virtual Environments and requirements.txt

By default, pip installs packages globally, for every program that uses that Python interpreter. That breaks down quickly: project A needs version 1 of a library, project B needs version 2, and only one version can be installed at a time. Upgrading for one project silently breaks the other.
A virtual environment is an isolated folder containing its own copy of python, pip and its own site-packages. Each project gets its own environment, so their dependencies never collide. The standard library's venv module creates them. 
# Create an environment in a folder called .venv (inside your project)
python -m venv .venv

# Activate it
.venv\Scripts\activate          # Windows (cmd / PowerShell)
source .venv/bin/activate       # macOS / Linux

# Now "python" and "pip" refer to the environment
python -m pip install requests
deactivate                      # return to the global interpreter
You can check which environment is active from Python itself: inside a virtual environment, sys.prefix (the environment) differs from sys.base_prefix (the Python installation it was created from). 
import sys

in_venv = sys.prefix != sys.base_prefix
print("Running inside a virtual environment:", in_venv)
print("Interpreter:", sys.executable)

Reproducing an environment with requirements.txt

Environments are not copied or committed to version control (add .venv/ to your .gitignore). Instead, you record the list of packages so that a teammate, a server or your future self can rebuild an identical environment. 
python -m pip freeze > requirements.txt     # save exact versions of everything installed
python -m pip install -r requirements.txt   # recreate them in a fresh environment

# requirements.txt
certifi==2024.8.30
charset-normalizer==3.4.0
idna==3.10
requests==2.32.3
urllib3==2.2.3
Pinning exact versions (==) makes deployments reproducible. Libraries meant to be installed by others should instead declare looser ranges (for example requests>=2.30) in pyproject.toml, so they don't conflict with other packages. Tools such as pip-tools, poetry and uv automate this split between "what I need" and "exactly what got installed".

Docstrings for Modules, Classes and Functions

A docstring is a string literal placed as the first statement of a module, class or function. Unlike a comment, it is kept at run time in the object's __doc__ attribute, so tools can use it: help() in the interactive prompt, IDE tooltips, and documentation generators such as Sphinx or MkDocs. In a team, docstrings are the contract between the person who wrote a function and everyone who calls it.
PEP 257 describes the conventions:
  • Always use triple double quotes """...""".
  • The first line is a short, one-sentence summary ending with a period.
  • If more is needed, leave a blank line, then explain the details.
  • Describe what the code does and how to use it (arguments, return value, exceptions raised), not how it is implemented internally.
"""Utilities for working with words and vocabulary lists.

This module is used by the quiz generator. The main entry point is
find_anagrams().
"""


class Vocabulary:
    """A collection of known words, stored in lowercase.

    Attributes:
        words: the set of words in the vocabulary.
    """

    def __init__(self, words):
        self.words = {w.lower() for w in words}


def find_anagrams(word, vocabulary):
    """Return the words in a vocabulary that are anagrams of a word.

    The comparison ignores case. The word itself is not included.

    Args:
        word: the word to rearrange.
        vocabulary: a Vocabulary instance to search.

    Returns:
        A sorted list of matching words. The list is empty if nothing matches.

    Raises:
        ValueError: if word is an empty string.
    """
    if not word:
        raise ValueError("word must not be empty")
    key = sorted(word.lower())
    return sorted(w for w in vocabulary.words
                  if w != word.lower() and sorted(w) == key)


vocab = Vocabulary(["Listen", "silent", "enlist", "google", "tinsel"])
print(find_anagrams("listen", vocab))      # ['enlist', 'silent', 'tinsel']
print(find_anagrams.__doc__.splitlines()[0])
# Return the words in a vocabulary that are anagrams of a word.
The example uses the popular Google style (Args:, Returns:, Raises:). NumPy style and reStructuredText (Sphinx) style are also common. Which one you pick matters less than using it consistently across the project. When you use type hints, there is no need to repeat the types in the docstring.
An out-of-date docstring is worse than none, because readers trust it. Update the docstring in the same change that modifies the behaviour.

Packages to Organize Modules

As a program grows, a single module becomes hard to navigate. A package is a directory of modules containing an __init__.py file. Packages give you namespaces: two modules can both be called utils.py as long as they live in different packages, and imports show clearly where everything comes from. 
shop/
    __init__.py          # marks "shop" as a package; runs on "import shop"
    models.py
    pricing.py
    payments/
        __init__.py
        card.py
Inside a package, modules can refer to each other with relative imports: a single dot means "the current package", two dots mean "the parent package". 
# shop/models.py
class Product:
    def __init__(self, name, price):
        self.name = name
        self.price = price

# shop/pricing.py
from .models import Product          # same package

def apply_discount(product: Product, percent: float) -> float:
    return round(product.price * (1 - percent / 100), 2)

def _round_to_cents(value):          # leading underscore: internal helper
    return round(value, 2)

# shop/payments/card.py
from ..pricing import apply_discount  # parent package

Defining a public API with __init__.py and __all__

The __init__.py file can re-export the names that users of the package are meant to use, so they can write from shop import Product without knowing the internal module layout. You are then free to reorganize the internal modules later without breaking anyone.
The __all__ list declares the public names of a module. It controls what from module import * imports, and tells readers and tools which names are supported. 
# shop/__init__.py
"""A tiny online shop package."""
from .models import Product
from .pricing import apply_discount

__all__ = ["Product", "apply_discount"]

# main.py (next to the shop/ folder)
from shop import Product, apply_discount

book = Product("Python Book", 40.0)
print(apply_discount(book, 25))   # 30.0
  • Relative imports only work inside a package. Running a module directly with python shop/pricing.py fails with ImportError: attempted relative import with no known parent package. Run it as a module instead: python -m shop.pricing.
  • Don't name your own files after standard library or installed modules (random.py, json.py, requests.py). Your file shadows the real one and imports break in confusing ways.
  • Avoid from module import * in application code: it hides where names come from and can silently overwrite existing names.

Define a Root Exception to Insulate Callers from APIs

When you write a module or package that other people use, the exceptions it raises are part of its API. If your code raises a mixture of built-in exceptions (ValueError, KeyError...), callers can't tell apart "you called my API incorrectly" from "there is a bug inside the library".
A better design is to define a root exception for your module, and make every exception you raise intentionally inherit from it. This gives callers three benefits:
  1. They can catch everything your API raises on purpose with a single except clause.
  2. Any exception that is not a subclass of your root (for example a TypeError from a typo in your code) reveals a bug in your library rather than a misuse, and can be reported separately.
  3. You can add more specific subclasses later without breaking existing callers.
# --- weather.py: the library -----------------------------------------
class WeatherError(Exception):
    """Base class for all errors raised by this module."""

class InvalidCityError(WeatherError):
    """The requested city name is not valid."""

class ServiceUnavailableError(WeatherError):
    """The weather service could not be reached."""

_DATA = {"paris": 18, "tokyo": 24}

def temperature(city):
    if not city.isalpha():
        raise InvalidCityError(f"invalid city name: {city!r}")
    if city.lower() == "atlantis":
        raise ServiceUnavailableError("no station there")
    return _DATA.get(city.lower(), 20)

# --- the caller ------------------------------------------------------
import logging

for city in ["Paris", "N3w York", "Atlantis"]:
    try:
        print(city, temperature(city))
    except InvalidCityError as exc:
        print("bad input:", exc)               # a specific, expected case
    except WeatherError as exc:
        print("API problem:", exc)             # anything else the module raises on purpose
    except Exception:
        logging.exception("Bug in the weather module!")  # not ours to swallow silently
        raise

# Paris 18
# bad input: invalid city name: 'N3w York'
# API problem: no station there
It is fine for specific errors to inherit from both your root and a related built-in, for example class InvalidCityError(WeatherError, ValueError), so that code that already catches ValueError keeps working.

Breaking Circular Dependencies

A circular dependency happens when module A imports module B, and module B (directly or through other modules) imports module A. It often appears when a team splits a large program into modules. To understand the error, recall what import a actually does:
  1. Create an empty module object and register it in sys.modules.
  2. Execute the module's code from top to bottom, filling in its attributes.
If, during step 2, a imports b, and b does from a import something, Python finds the half-built module a in sys.modules, and something has not been defined yet. 
# dialog.py
import app

class Dialog:
    def __init__(self):
        self.save_dir = app.prefs.save_dir    # needs app's preferences

save_dialog = Dialog()                       # runs at import time!

# app.py
import dialog

class Prefs:
    save_dir = "/tmp"

prefs = Prefs()

> python -c "import app"
AttributeError: partially initialized module 'app' has no attribute 'prefs' (most likely due to a circular import)
Ways to fix it, from best to least preferred:
  1. Refactor: move the shared pieces into a third module that both import, so the dependency graph has no cycle (for example, move Prefs into config.py). This is usually the cleanest fix, because a cycle is often a sign that responsibilities are mixed up.
  2. Avoid work at import time: modules should only define functions, classes and constants when imported. Do the setup in an explicit configure() function that the main program calls once everything is imported.
  3. Dynamic import: move the import statement inside the function that needs it. It then runs at call time, when both modules are fully loaded. It works, but hides dependencies and should be a last resort.
# dialog.py  (fixed: nothing depends on app at import time)
import app

class Dialog:
    def __init__(self):
        self.save_dir = None

save_dialog = Dialog()

def configure():
    save_dialog.save_dir = app.prefs.save_dir

# main.py
import app
import dialog

dialog.configure()                  # called after every module is loaded
print(dialog.save_dialog.save_dir)  # /tmp
If the cycle exists only because of type hints, import the module under if typing.TYPE_CHECKING:. That block is skipped at run time but still read by type checkers.

Use warnings to Refactor and Migrate Usage

Changing a function used by many other people (or many places in a large codebase) is difficult: if you rename an argument or remove a function overnight, every caller breaks at once. A gentler approach is a deprecation period: keep the old behaviour working for a while, but emit a warning telling callers what to change.
The warnings module does this. Unlike an exception, a warning does not stop the program; it prints a message (once per location, by default) and execution continues. 
import warnings

def print_distance(speed, duration, *, speed_units=None, time_units=None):
    if speed_units is None:
        warnings.warn(
            "speed_units will become required in version 3.0; pass it explicitly",
            DeprecationWarning,
            stacklevel=2,          # point the warning at the CALLER's line, not this one
        )
        speed_units = "mph"
    if time_units is None:
        time_units = "hours"
    print(f"{speed * duration} miles")

print_distance(60, 2)                     # still works, but warns
print_distance(60, 2, speed_units="mph")  # updated call: no warning
# Printed to stderr:
# example.py:15: DeprecationWarning: speed_units will become required in version 3.0; pass it explicitly
#   print_distance(60, 2)                     # still works, but warns
# Printed to stdout:
# 120 miles
# 120 miles
The stacklevel=2 argument is essential: without it, the warning would report the line inside print_distance, which is useless to the caller who needs to find their outdated call.

Controlling warnings

By default, DeprecationWarning is only shown when triggered by code in __main__ or in test runners; it is hidden in imported library code so that end users are not bothered. While migrating, you can make warnings visible, or even turn them into errors so that a test suite fails on every remaining old-style call: 
python -W error::DeprecationWarning my_script.py   # every DeprecationWarning becomes an exception
python -W default my_script.py                     # show all warnings once per location

import warnings

def old_api():
    warnings.warn("old_api() is deprecated; use new_api()", DeprecationWarning, stacklevel=2)
    return 42

# Turn warnings into errors inside a block (useful in tests)
with warnings.catch_warnings():
    warnings.simplefilter("error", DeprecationWarning)
    try:
        old_api()
    except DeprecationWarning as exc:
        print("caught:", exc)        # caught: old_api() is deprecated; use new_api()

# Record warnings to check them in a test
with warnings.catch_warnings(record=True) as caught:
    warnings.simplefilter("always")
    old_api()
print(len(caught), caught[0].category.__name__)   # 1 DeprecationWarning
Python 3.13 added the @warnings.deprecated("message") decorator, which emits the warning at run time and also lets type checkers flag uses of the deprecated function.

Static Analysis with typing and mypy

Python is dynamically typed: a variable can hold any type, and errors like passing a string where a number is expected are only discovered when that line runs, possibly in production. Type hints let you annotate the expected types of arguments, return values and variables. Python itself ignores them at run time, but static type checkers such as mypy or pyright read your code without running it and report inconsistencies.
In a team, hints also serve as always-up-to-date documentation, and make IDE autocompletion and refactoring much more accurate. 
from dataclasses import dataclass
from typing import Protocol


@dataclass
class Item:
    name: str
    price: float
    quantity: int = 1


def total(items: list[Item], tax_rate: float = 0.0) -> float:
    subtotal = sum(i.price * i.quantity for i in items)
    return round(subtotal * (1 + tax_rate), 2)


def find(items: list[Item], name: str) -> Item | None:   # may return None
    for item in items:
        if item.name == name:
            return item
    return None


class Greeter(Protocol):            # "anything with a greet() method"
    def greet(self) -> str: ...


def welcome(g: Greeter) -> None:
    print(g.greet())


cart = [Item("pen", 1.5, 4), Item("book", 12.0)]
print(total(cart, tax_rate=0.2))    # 21.6
found = find(cart, "pen")
if found is not None:               # narrowing: mypy now knows found is an Item
    print(found.price)              # 1.5
Install mypy in your virtual environment and run it on your code. Suppose someone writes these lines below the code above: 
total(cart, tax_rate="20%")         # wrong type
print(find(cart, "pen").price)      # find() may return None

> python -m pip install mypy
> python -m mypy shop.py
shop.py:37: error: Argument "tax_rate" to "total" has incompatible type "str"; expected "float"  [arg-type]
shop.py:38: error: Item "None" of "Item | None" has no attribute "price"  [union-attr]
Found 2 errors in 1 file (checked 1 source file)
Neither bug would have been noticed until the program ran those exact lines. The second one is especially valuable to catch: forgetting that a function can return None is one of the most common causes of crashes.
  • Type hints are not checked at run time. total(cart, tax_rate="20%") still runs (and fails or misbehaves) unless you use a checker.
  • Adopt typing gradually: unannotated functions are not checked by default, so start with the most important modules, and use mypy --strict once a module is fully annotated.
  • Use Any and # type: ignore sparingly; each one switches off the checker exactly where it might be needed.

Code Style and Linters

Code is read far more often than it is written. When everyone on a team formats code the same way, reviews focus on what the code does instead of on spaces and quotes. PEP 8 is Python's official style guide. Its most important rules:
  • Indent with 4 spaces; keep lines reasonably short (79 characters in PEP 8, 88 in black, often up to 100 in teams).
  • snake_case for functions, variables and modules; PascalCase for classes; UPPER_CASE for constants; a leading underscore for internal names.
  • Imports at the top of the file, one per line, grouped as standard library, third-party, then your own modules.
  • Compare with None using is / is not; test emptiness with if not items: rather than if len(items) == 0:.
  • Two blank lines around top-level functions and classes, one between methods.
# Hard to read: works, but breaks many conventions
import os,sys
def CalcAvg( L ):
  if len(L)==0 : return None
  return sum(L)/len(L)

# PEP 8 style
def calculate_average(values):
    if not values:
        return None
    return sum(values) / len(values)


print(calculate_average([3, 4, 5]))  # 4.0

Let tools do the work: formatters and linters

Nobody should enforce style by hand in code reviews. Two kinds of tools automate it:
  • A formatter rewrites your code into a consistent layout. black is "opinionated": it has almost no options, which ends formatting debates. ruff format is a faster, compatible alternative.
  • A linter analyses code for likely bugs and bad practices: unused imports and variables, undefined names, mutable default arguments, bare except... ruff (very fast, written in Rust) has largely replaced flake8, isort and many plugins.
> python -m pip install ruff
> ruff check --output-format concise bad_style.py
bad_style.py:2:1: I001 [*] Import block is un-sorted or un-formatted
bad_style.py:2:8: F401 [*] `os` imported but unused
bad_style.py:2:11: F401 [*] `sys` imported but unused
Found 3 errors.
[*] 3 fixable with `--fix`.
> ruff check --fix .         # fix what can be fixed automatically
> ruff format .              # reformat every file in the project
Run the formatter and linter automatically: configure your editor to format on save, and use a pre-commit hook or a CI job so that unformatted code can't be merged. When a style rule and readability disagree, PEP 8 itself says to prefer readability and consistency with the surrounding code.

Project Layout and pyproject.toml

A predictable project structure helps new contributors find their way and lets tools work without extra configuration. A widely recommended layout is the src layout: 
my_project/
    pyproject.toml          # project metadata, dependencies and tool settings
    README.md               # what it is and how to install / use it
    LICENSE
    .gitignore              # includes .venv/, __pycache__/, dist/
    src/
        my_package/
            __init__.py
            core.py
            cli.py
    tests/
        test_core.py
Why put the package under src/? Because then it cannot be imported by accident just because you run Python from the project folder. Your tests have to use the installed package, exactly as your users will, which catches packaging mistakes (such as a missing file) early.
pyproject.toml (PEP 518 / PEP 621) is the single, standard configuration file of a modern Python project. It replaces the older setup.py, setup.cfg and many tool-specific config files. It is written in TOML, a simple configuration format. 
[build-system]
requires = ["setuptools>=68"]
build-backend = "setuptools.build_meta"

[project]
name = "my-package"
version = "0.1.0"
description = "A short description of the project."
readme = "README.md"
requires-python = ">=3.10"
dependencies = [
    "requests>=2.30",
]

[project.optional-dependencies]
dev = ["pytest", "mypy", "ruff"]

[project.scripts]
my-tool = "my_package.cli:main"       # creates a "my-tool" command on install

[tool.ruff]
line-length = 100

[tool.mypy]
strict = true
With this file in place, a new contributor needs only a few commands to get a working development setup. The -e (editable) flag links the environment to your source folder, so code changes take effect without reinstalling. 
git clone https://example.com/my_project.git
cd my_project
python -m venv .venv
.venv\Scripts\activate
python -m pip install -e ".[dev]"    # the package itself + development tools
pytest                               # run the tests
python -m build                      # (optional) build a wheel to share or upload to PyPI
Your code can read its own metadata at run time, which avoids writing the version number in two places: 
from importlib.metadata import version, PackageNotFoundError

try:
    print(version("pip"))          # e.g. 24.2 (works for any installed package)
    print(version("my-package"))   # your own package, once it is installed
except PackageNotFoundError as exc:
    print("not installed:", exc)
Things to Remember
  • One virtual environment per project; never commit it.
  • Write docstrings and type hints for everything other people will call.
  • Give your package a clear public API (__init__.py, __all__) and a root exception.
  • Let formatters, linters and type checkers enforce consistency, ideally on every commit.
  • Keep project configuration in pyproject.toml.
