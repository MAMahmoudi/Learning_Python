Robustness and Performance

Take Advantage of try/except/else/finally

A try statement can have four kinds of blocks, and each one has a distinct job:
  • try: the code that might raise an exception. Keep it as small as possible.
  • except: runs only if a matching exception was raised in the try block.
  • else: runs only if the try block finished without an exception.
  • finally: always runs, whether an exception occurred, was handled, or was not handled. It is the place for clean-up such as closing files.
Why have an else block at all? Because anything you put inside try is covered by the except clauses. If you put the "success" code in the try too, an unrelated error from it could be caught by mistake and reported as the wrong problem. Moving it to else makes it clear which line you expect to fail. 
import json

def load_settings(text):
    try:
        data = json.loads(text)            # the only line we expect may fail
    except json.JSONDecodeError as exc:
        print(f"Invalid JSON: {exc.msg}")
        return None
    else:
        # Runs only on success. A KeyError here is a real bug and is NOT
        # silently swallowed by the except clause above.
        print("Parsed OK, theme =", data["theme"])
        return data
    finally:
        print("finished parsing attempt")   # always runs, even after return

load_settings('{"theme": "dark"}')
# Parsed OK, theme = dark
# finished parsing attempt
load_settings('{theme: dark}')
# Invalid JSON: Expecting property name enclosed in double quotes
# finished parsing attempt

finally for clean-up

Open the resource before the try. If opening fails, there is nothing to close, and the finally block should not run. 
import os
import tempfile

path = os.path.join(tempfile.gettempdir(), "demo_finally.txt")
handle = open(path, "w", encoding="utf-8")   # may raise OSError: keep it outside try
try:
    handle.write("hello")
    raise RuntimeError("something went wrong while writing")
except RuntimeError as exc:
    print("handled:", exc)
finally:
    handle.close()                            # runs in every case
    print("closed:", handle.closed)           # closed: True
os.remove(path)
  • Never write a bare except: or except Exception: pass. It hides bugs (even typos and KeyboardInterrupt in the bare case). Catch the specific exceptions you know how to handle.
  • A return inside finally silently discards any exception in flight. Avoid it (Python 3.14 even warns about it).

contextlib and with Statements

The try/finally pattern for "set up, do work, always clean up" is so common that Python gives it its own syntax: the with statement. An object usable in with is a context manager: its __enter__ method runs at the start of the block and its __exit__ method runs at the end, even if an exception is raised. Files, locks and database connections all work this way.
Instead of writing a class with two special methods, you can turn a simple generator into a context manager using the @contextlib.contextmanager decorator. Everything before yield is the set-up, the yielded value is what as receives, and everything after yield is the clean-up. 
from contextlib import contextmanager
import logging

logging.basicConfig(level=logging.WARNING, format="%(levelname)s: %(message)s")

@contextmanager
def log_level(level, name):
    logger = logging.getLogger(name)
    old_level = logger.getEffectiveLevel()
    logger.setLevel(level)             # set-up
    try:
        yield logger                   # the body of the with block runs here
    finally:
        logger.setLevel(old_level)     # clean-up, even if the body raises

with log_level(logging.DEBUG, "my-app") as logger:
    logger.debug("visible: level temporarily lowered to DEBUG")

logging.getLogger("my-app").debug("hidden: level restored to WARNING")
# DEBUG: visible: level temporarily lowered to DEBUG
Always wrap the yield in try/finally. Otherwise, if the body of the with block raises an exception, it is re-raised at the yield and your clean-up code never runs.

Other useful contextlib helpers

  • suppress(*exceptions): ignore specific, expected exceptions in a readable way.
  • closing(obj): call obj.close() at the end for objects that have a close method but are not context managers.
  • ExitStack: manage a variable number of context managers, for example opening a list of files whose length is only known at run time.
from contextlib import suppress, ExitStack
import os
import tempfile

with suppress(FileNotFoundError):
    os.remove("this_file_does_not_exist.txt")   # no error, no noise
print("still running")                          # still running

folder = tempfile.mkdtemp()
names = [os.path.join(folder, f"part{i}.txt") for i in range(3)]
with ExitStack() as stack:
    files = [stack.enter_context(open(n, "w", encoding="utf-8")) for n in names]
    for i, f in enumerate(files):
        f.write(f"chunk {i}")
print(all(f.closed for f in files))             # True: all three were closed

Use datetime and zoneinfo Instead of time for Local Clocks

The UTC (Coordinated Universal Time) is the standard, time-zone-independent reference for time. Computers should store and compute in UTC, and convert to a local time zone only when displaying times to people.
The time module is a thin wrapper around the operating system's C functions. It can only convert between UTC and the machine's own local zone, and its behaviour differs between platforms. To work with arbitrary time zones, use the datetime module together with zoneinfo (standard library since Python 3.9), which uses the official IANA time zone database and handles daylight saving time correctly.

Naive vs aware datetimes

A naive datetime has no time zone attached (tzinfo is None); it is ambiguous, like a meeting time written without a city. An aware datetime knows its zone and represents an exact instant. Always use aware datetimes when time zones matter. 
from datetime import datetime, timedelta, timezone
from zoneinfo import ZoneInfo

# A flight departs New York at 18:30 local time
departure = datetime(2024, 3, 9, 18, 30, tzinfo=ZoneInfo("America/New_York"))
print(departure)                 # 2024-03-09 18:30:00-05:00

# Store it as UTC
as_utc = departure.astimezone(timezone.utc)
print(as_utc)                    # 2024-03-09 23:30:00+00:00

# Show the arrival (7h45 later) in Paris local time
arrival = as_utc + timedelta(hours=7, minutes=45)
print(arrival.astimezone(ZoneInfo("Europe/Paris")))   # 2024-03-10 08:15:00+01:00

# The current moment, as an aware datetime
now = datetime.now(timezone.utc)
print(now.tzinfo)                # UTC
Daylight saving time is handled for you. On 10 March 2024, clocks in New York jumped from 2:00 to 3:00, so the UTC offset changes from -05:00 to -04:00: 
from datetime import datetime, timedelta, timezone
from zoneinfo import ZoneInfo

ny = ZoneInfo("America/New_York")
before = datetime(2024, 3, 10, 1, 30, tzinfo=ny)
after = (before.astimezone(timezone.utc) + timedelta(hours=1)).astimezone(ny)
print(before)   # 2024-03-10 01:30:00-05:00
print(after)    # 2024-03-10 03:30:00-04:00  (one real hour later)
  • datetime.utcnow() returns a naive datetime and is deprecated since Python 3.12. Use datetime.now(timezone.utc).
  • Comparing or subtracting a naive and an aware datetime raises TypeError.
  • Do arithmetic in UTC: adding a timedelta to an aware local datetime works on "wall clock" time and can give surprising results across a DST change.
  • On Windows, the time zone database may not be included with Python. If ZoneInfo raises ZoneInfoNotFoundError, run pip install tzdata.

Serializing Safely: pickle, copyreg and json

Serialization turns Python objects into bytes or text so they can be saved to a file or sent over a network, and later turned back into objects. The pickle module can serialize almost any Python object, including your own classes. 
import pickle

class GameState:
    def __init__(self, level=0, lives=4):
        self.level = level
        self.lives = lives

state = GameState(level=3)
data = pickle.dumps(state)            # bytes
restored = pickle.loads(data)
print(restored.level, restored.lives)  # 3 4
Never unpickle data from an untrusted source. A pickle is not just data; it is a small program that tells Python which objects to build and which functions to call. A malicious pickle can run any command on your computer the moment you call pickle.loads(). Use pickle only for data your own program wrote and nobody else could tamper with.

Making pickles survive class changes with copyreg

Pickle stores an object's attribute dictionary and the import path of its class. If you later add a new attribute to the class, old pickles restore objects without that attribute, because __init__ is not called on unpickling. The copyreg module lets you register a function that controls how objects are pickled, so you can make unpickling go through a function that fills in defaults and handles versions. 
import copyreg
import pickle

class GameState:
    def __init__(self, level=0, lives=4, points=0):   # 'points' added in version 2
        self.level = level
        self.lives = lives
        self.points = points

def unpickle_game_state(kwargs):
    return GameState(**kwargs)          # missing attributes get their defaults

def pickle_game_state(state):
    return unpickle_game_state, (state.__dict__,)

copyreg.pickle(GameState, pickle_game_state)

# Simulate an old pickle that was saved before 'points' existed
old = GameState(level=2)
del old.points
data = pickle.dumps(old)

restored = pickle.loads(data)
print(restored.__dict__)   # {'level': 2, 'lives': 4, 'points': 0}

Prefer json for data exchange

For configuration files, APIs and anything shared between programs or people, prefer json. It can only represent plain data (dicts, lists, strings, numbers, booleans and None), so loading it can never execute code. It is also readable by humans and by every other programming language. Convert your objects to and from dictionaries explicitly. 
import json
from dataclasses import dataclass, asdict

@dataclass
class GameState:
    level: int = 0
    lives: int = 4

text = json.dumps(asdict(GameState(level=5)))
print(text)                                 # {"level": 5, "lives": 4}
restored = GameState(**json.loads(text))
print(restored)                             # GameState(level=5, lives=4)

Use decimal When Precision Is Paramount

Python's float uses binary floating point (IEEE 754). Most decimal fractions, like 0.1, cannot be represented exactly in binary, just as 1/3 cannot be written exactly in decimal. The tiny errors are fine for science and graphics, but unacceptable for money, where every cent must add up. 
print(0.1 + 0.2)            # 0.30000000000000004
print(0.1 + 0.2 == 0.3)     # False
print(round(2.675, 2))      # 2.67 (not 2.68: 2.675 is stored as 2.67499999...)
The decimal module performs exact base-10 arithmetic and lets you choose exactly how rounding works. Use quantize() to round to a fixed number of places with an explicit rounding mode. 
from decimal import Decimal, ROUND_HALF_UP, ROUND_UP

print(Decimal("0.1") + Decimal("0.2"))                    # 0.3
print(Decimal("0.1") + Decimal("0.2") == Decimal("0.3"))  # True

# Price of a 5-minute international call at $1.45 per minute
cost = Decimal("1.45") * 5 / 60
print(cost)                                                # 0.1208333333333333333333333333
print(cost.quantize(Decimal("0.01"), rounding=ROUND_HALF_UP))  # 0.12
print(cost.quantize(Decimal("0.01"), rounding=ROUND_UP))       # 0.13  (never undercharge)
Create decimals from strings (or integers), not floats. Decimal(0.1) faithfully copies the float's error: Decimal('0.1000000000000000055511151231257827021181583404541015625').
If you need exact rational numbers such as 1/3, the fractions.Fraction class stores a numerator and denominator with no rounding at all. Decimal arithmetic is slower than float, so use it where correctness matters, not everywhere.

Profile Before Optimizing

Programmers are notoriously bad at guessing where their programs are slow. Time spent "optimizing" code that barely runs is wasted, and makes the code harder to read. Instead, measure first:
  • timeit times small snippets precisely, running them many times to smooth out noise.
  • cProfile runs a whole program and records how much time is spent in every function. pstats sorts and prints the results.
import timeit

setup = "data = list(range(10_000))"
t_list = timeit.timeit("9_999 in data", setup=setup, number=1_000)
t_set = timeit.timeit("9_999 in s", setup=setup + "; s = set(data)", number=1_000)
print(f"list membership: {t_list:.4f}s")   # e.g. 0.0600s
print(f"set membership:  {t_set:.6f}s")    # e.g. 0.000020s  (thousands of times faster)
From a terminal, timeit chooses the number of repetitions for you: 
python -m timeit -s "data = list(range(10_000))" "9_999 in data"
python -m cProfile -s cumulative my_script.py
Here is a profiling session inside Python. The output columns mean: ncalls (number of calls), tottime (time spent in the function itself, excluding the functions it calls) and cumtime (time including everything it calls). 
import cProfile
import pstats
import io

def insertion_sort(data):
    result = []
    for value in data:
        insert_value(result, value)
    return result

def insert_value(array, value):
    for i, existing in enumerate(array):      # linear scan: the hidden bottleneck
        if existing > value:
            array.insert(i, value)
            return
    array.append(value)

import random
data = [random.randint(0, 10_000) for _ in range(3_000)]

profiler = cProfile.Profile()
profiler.runcall(insertion_sort, data)

out = io.StringIO()
stats = pstats.Stats(profiler, stream=out)
stats.strip_dirs().sort_stats("cumulative").print_stats(4)
print(out.getvalue())
# Shows that nearly all the time is spent in insert_value (3000 calls).
# Replacing the linear scan with bisect.insort (see below) makes it far faster.
Profile with realistic input. A bottleneck that only appears with large data will not show up if you profile with ten items.

Prefer deque for Producer-Consumer Queues

A first-in, first-out (FIFO) queue is easy to build with a list: append() to add at the end and pop(0) to take from the front. The problem is that pop(0) must shift every remaining element one position to the left, so it costs time proportional to the length of the list (O(n)). As the queue grows, the program slows down dramatically.
collections.deque (double-ended queue) is designed for this: adding or removing at either end is O(1), no matter how long it is. 
from collections import deque
import timeit

queue = deque()
queue.append("email 1")      # producer adds to the right
queue.append("email 2")
queue.appendleft("urgent")   # can also add to the left
print(queue.popleft())       # urgent   (consumer takes from the left)
print(queue)                 # deque(['email 1', 'email 2'])

n = 20_000   # empty a 20,000-item queue completely
t_list = timeit.timeit("q.pop(0)", setup=f"q = list(range({n}))", number=n)
t_deque = timeit.timeit("q.popleft()",
                        setup=f"from collections import deque; q = deque(range({n}))", number=n)
print(f"list.pop(0):     {t_list:.4f}s")    # e.g. 0.4000s (grows with the square of n)
print(f"deque.popleft(): {t_deque:.4f}s")   # e.g. 0.0006s
A deque with a maxlen automatically discards items from the opposite end when it is full, which is perfect for "keep the last N items": 
from collections import deque

recent = deque(maxlen=3)
for page in ["home", "about", "blog", "contact", "shop"]:
    recent.append(page)
print(list(recent))   # ['blog', 'contact', 'shop']
Accessing an element in the middle of a deque by index is O(n). A deque is a queue, not a replacement for a list when you need random access. For queues shared between threads, use queue.Queue, which adds blocking and locking.

Use bisect for Searching Sorted Sequences

Finding a value in a list with list.index() or in checks every element in turn: O(n). If the list is already sorted, you can do much better with binary search: look at the middle element, discard the half that cannot contain the value, and repeat. Each step halves the search space, so a list of one million items needs only about 20 comparisons (O(log n)).
The bisect module implements this:
  • bisect_left(a, x) returns the index where x would be inserted to keep a sorted (before any equal items).
  • bisect_right(a, x) (alias bisect) does the same, after any equal items.
  • insort(a, x) inserts x at the correct position.
from bisect import bisect_left, insort

data = list(range(0, 1_000_000, 2))      # sorted even numbers

def contains(sorted_list, x):
    i = bisect_left(sorted_list, x)
    return i < len(sorted_list) and sorted_list[i] == x

print(contains(data, 777_778))  # True
print(contains(data, 777_777))  # False

scores = [12, 45, 67, 89]
insort(scores, 50)
print(scores)                   # [12, 45, 50, 67, 89]
bisect is also handy for mapping numbers to ranges, such as grade boundaries: 
from bisect import bisect_right

def grade(score, breakpoints=(60, 70, 80, 90), grades="FDCBA"):
    return grades[bisect_right(breakpoints, score)]

print([grade(s) for s in (33, 60, 77, 89, 90, 100)])  # ['F', 'D', 'C', 'B', 'A', 'A']
bisect does not check that the list is sorted. On unsorted data it silently returns wrong answers. Also, insort finds the position in O(log n) but inserting into a list is still O(n), because elements must be shifted.
Since Python 3.10, all bisect functions accept a key argument, so you can search a list of records sorted by one field.

Use heapq for Priority Queues

Sometimes items should not be processed in arrival order but by priority: the most urgent support ticket first, the next timer to expire first, the shortest path first. Sorting the whole list every time something is added would be O(n log n) per insertion.
A heap is a list arranged so that the smallest item is always at index 0. The heapq module maintains this arrangement with O(log n) insertions and removals:
  • heappush(heap, item) adds an item.
  • heappop(heap) removes and returns the smallest item.
  • heapify(list) turns an existing list into a heap in O(n).
  • nsmallest(k, data) / nlargest(k, data) pick the top k items without sorting everything.
import heapq
import itertools

tasks = []
counter = itertools.count()    # tie-breaker: keeps insertion order for equal priorities

def add_task(priority, name):
    # Tuples compare element by element: priority first, then the counter
    heapq.heappush(tasks, (priority, next(counter), name))

add_task(3, "write docs")
add_task(1, "fix production bug")
add_task(2, "review pull request")
add_task(1, "reply to customer")

while tasks:
    priority, _, name = heapq.heappop(tasks)
    print(priority, name)
# 1 fix production bug
# 1 reply to customer
# 2 review pull request
# 3 write docs

prices = [42, 7, 19, 88, 3, 56]
print(heapq.nlargest(2, prices))   # [88, 56]
print(heapq.nsmallest(2, prices))  # [3, 7]
  • heapq is a min-heap. For a max-heap, push negated priorities (-priority).
  • Without the tie-breaking counter, two items with the same priority would be compared by their next field. If that field is not comparable (a dict, a custom object), you get a TypeError.
  • A heap is not sorted: only heap[0] is guaranteed to be the smallest. Do not iterate over it expecting order.

Zero-Copy with memoryview and bytearray

Slicing a bytes object creates a new copy of the data. When a program handles large binary data, such as network packets, video frames or file chunks, those copies waste memory and CPU time.
A memoryview wraps any object that supports the buffer protocol (bytes, bytearray, array.array, NumPy arrays) and lets you slice it without copying: the slice is just a window onto the same memory. 
import timeit

data = b"x" * 10_000_000          # 10 MB

t_copy = timeit.timeit(lambda: data[1_000:5_000_000], number=50)
view = memoryview(data)
t_view = timeit.timeit(lambda: view[1_000:5_000_000], number=50)
print(f"bytes slice:      {t_copy * 1e6 / 50:9.1f} microseconds")   # e.g. 600 microseconds
print(f"memoryview slice: {t_view * 1e6 / 50:9.1f} microseconds")   # e.g. 0.2 microseconds

chunk = view[0:5]
print(chunk.tobytes())            # b'xxxxx' (copy only when you really need bytes)
bytes is immutable, so a view of it is read-only. A bytearray is the mutable version of bytes. Combining it with memoryview lets you write into a part of a buffer in place, for example with socket.recv_into() or file.readinto(), which fill an existing buffer instead of allocating a new one each time. 
import io

buffer = bytearray(12)                     # pre-allocated, zero-filled
view = memoryview(buffer)

view[0:5] = b"Hello"                       # write through the view
view[5:7] = b", "
print(buffer)                              # bytearray(b'Hello, \x00\x00\x00\x00\x00')

stream = io.BytesIO(b"World")
n = stream.readinto(view[7:])              # read straight into the free space, no copy
print(n, bytes(buffer))                    # 5 b'Hello, World'
While a memoryview of a bytearray exists, the bytearray cannot be resized (append raises BufferError). Call view.release() or use the view in a with block when you are done with it.

Caching Results with functools.lru_cache and cache

If a function is pure (its result depends only on its arguments and it has no side effects) and it is called repeatedly with the same arguments, you can store results and return them instantly next time. This is called memoization.
functools.cache (Python 3.9+) remembers every result forever. functools.lru_cache(maxsize=N) keeps only the N most recently used results, which bounds memory use. 
from functools import cache, lru_cache
import time

def fib_slow(n):
    return n if n < 2 else fib_slow(n - 1) + fib_slow(n - 2)

@cache
def fib(n):
    return n if n < 2 else fib(n - 1) + fib(n - 2)

start = time.perf_counter()
print(fib_slow(30))                                 # 832040
print(f"no cache: {time.perf_counter() - start:.2f}s")    # e.g. 0.15s

start = time.perf_counter()
print(fib(30))                                      # 832040
print(f"cached:   {time.perf_counter() - start:.6f}s")    # e.g. 0.000020s
print(fib.cache_info())    # CacheInfo(hits=28, misses=31, maxsize=None, currsize=31)

@lru_cache(maxsize=128)
def lookup_country(code):
    print(f"  (expensive lookup for {code})")
    return {"fr": "France", "jp": "Japan"}.get(code, "Unknown")

lookup_country("fr")   # prints the expensive lookup message
lookup_country("fr")   # served from the cache: nothing printed
lookup_country.cache_clear()   # empty the cache when the data changes
  • All arguments must be hashable: calling a cached function with a list raises TypeError: unhashable type: 'list'. Pass a tuple instead.
  • Never cache functions with side effects or whose results change over time (reading the clock, a file or a database); you would get stale answers.
  • A cached function returns the same object each time. If the caller mutates a returned list or dict, the cache is corrupted for everyone.
  • Using @cache on a method keeps every self alive forever (memory leak). Consider functools.cached_property for per-instance values.
